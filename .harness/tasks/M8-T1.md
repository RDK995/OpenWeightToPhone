TASK

Goal:
Give the conversation store's persisted payload an explicit version, and make loading a
payload whose version is not recognised FAIL LOUDLY rather than silently reading it as
"no conversations". Today an unparseable or unexpected payload is silently replaced by
an empty list and the next write overwrites the user's entire transcript — that is the
"misread" this task exists to eliminate.

Tier: Mid. Reason: not low risk — this is the on-disk format every other component reads,
and wrong rejection semantics destroys the user's persisted transcript silently.

Relevant Requirements:
- FR3 — "The full transcript of each conversation is persisted locally on the phone."
- Architecture C11 (Storage Port), C8 (Conversation Store).

Acceptance Criteria (this is milestone M8's AC4):
- The persisted payload is written under a versioned key AND the payload itself carries
  an explicit schema version.
  - Keep the existing storage key constant `CONVERSATIONS_STORAGE_KEY`
    (`"phone-to-local-model:v1:conversations"`) exactly as it is — it is already
    versioned and other code imports it. Do not rename it.
  - Change the persisted VALUE from a bare JSON array to an envelope carrying the
    version, e.g. `{"version": 1, "conversations": [...]}`. Export the current version
    as a named constant (e.g. `CONVERSATIONS_SCHEMA_VERSION = 1`).
- A payload whose version is NOT the recognised one is REJECTED rather than misread:
  loading it must throw a distinguishable, exported error type (e.g.
  `UnknownStorageVersionError`, following the typed-error pattern already used in
  `web/src/api-client.ts` — read `HarnessApiError` there and match the house style).
  The error must carry the version that was found and the version that was expected.
- Rejection must NOT destroy data. When the version is unknown, the store must not write
  anything back over the stored payload. After a rejected load, the raw stored string
  must still be byte-identical to what was there before. Prove this with a test.
- A payload that is present but structurally invalid (not JSON at all, or JSON that is
  not a recognised envelope) is likewise rejected rather than silently becoming an empty
  list. Decide and document the single consistent behaviour; do not leave a silent
  swallow in place.
- Absent payload (key not present at all) is NOT an error — a first run must still yield
  an empty conversation list. This is the one case that stays quiet.
- All existing behaviour of the store is otherwise preserved: `loadConversations`,
  `getConversation`, `createConversation`, `saveConversation`, `appendTurn`,
  `setSessionId`, `setProfileId`, `recordProgress` keep their current signatures and
  semantics, including `loadConversations()` returning newest-first.
- The existing `normalizePending` backward-compatibility for a `pending` record lacking
  `partialText` is preserved inside the versioned envelope.
