TASK

Tier: Mid.
Named reason: **not low risk**. This task decides what happens to persisted resume
state when a connection fails, and getting it wrong is silent and expensive: if a
dropped stream clears `pending`, resume becomes impossible and the failure looks
exactly like a normal completion. It also has to distinguish a transport drop from
a cancel and from a client bug, which is precisely the distinction FR7 exists for.

Goal:
Make the session coordinator (component C9, `web/src/session-coordinator.ts`)
survive a dropped connection and resume from persisted state:
(a) a transport failure mid-stream must LEAVE the pending generation recorded,
    with the last seq and the partial text received so far, and
(b) a new `resumeIfInterrupted` must pick that up, resume the event stream, and
    reconcile the transcript — including a fallback when the resume point is
    refused.

Relevant Requirements:
FR7 — "On reconnect or return to foreground, resume the event stream via
`GET /v1/sessions/{id}/generations/{id}/events` using `Last-Event-ID` set to the
last received seq, yielding no gaps and no duplicates. Disconnecting is
distinguished from cancelling: a dropped connection leaves the generation running."

Requirements edge case — "`409 seq_not_available` on resume — the buffer has
discarded the requested seq; fall back to fetching the session and reconciling
from its recorded state."

Requirements Decisions — "The API document's 'Building a Client' step 5 is wrong.
It instructs clients to append the assistant's answer as a turn. ... A client that
also appended turns would duplicate them and corrupt the conversation." The service
appends BOTH the user turn and the assistant turn itself. `GET /v1/sessions/{id}`
is therefore the authoritative record of the conversation's turns.

AC5 (already owned by an earlier milestone, must not be broken) — "Exactly one user
turn and one assistant turn are recorded per generation ... No duplication."

The agreed architecture (`.harness/architecture.md`, "Interfaces") specifies the
C10 -> C9 interface as `send(...)`, `cancel(...)`, `resumeIfInterrupted(conversationId)`,
and the C9 -> C7 interface as including `resumeEvents(sessionId, generationId, lastSeq)`.

State already in place (do not re-implement, just use it):
- `web/src/api-client.ts` now has
  `resumeEvents(sessionId, generationId, lastSeq, options?: { signal?: AbortSignal })`
  returning `{ generationId, events }`, and `generate(sessionId, { profileId, prompt, signal? })`.
  A `409` with body `{"error":"seq_not_available","last_seq":N}` throws
  `HarnessApiError` with `code === "seq_not_available"`, `status === 409`, and
  `body.last_seq` intact.
- `web/src/conversation-store.ts`'s `PendingGeneration` is now
  `{ generationId: string; lastSeq: number; status: string; partialText: string }`,
  persisted through the storage port and read back by a freshly constructed store.

Acceptance Criteria:

1. `session-coordinator.ts` type-checks again. It currently constructs
   `PendingGeneration` literals at roughly lines 75 and 129 without `partialText`,
   which is a type error. Fix those by supplying the real accumulated text, not by
   hardcoding `""` at the point where text is known.

2. During `send`, each `recordProgress` call made while consuming the stream
   persists BOTH the current `lastSeq` AND the text accumulated so far, as
   `partialText`. After N content events have been consumed, a freshly constructed
   `ConversationStore` over the same `StoragePort` must report a `pending` whose
   `partialText` is the concatenation of those N deltas and whose `lastSeq` is the
   last seq seen.

3. **A transport failure mid-stream leaves `pending` set.** When the event
   iteration throws because the stream failed — an aborted fetch, a network error,
   or the existing "Stream ended without terminal event" condition — `send` must
   NOT clear pending. It must leave the persisted `pending` holding the
   generation id, the last seq actually received, the partial text actually
   received, and status `"in_flight"`, and then rethrow.

4. **A handler callback throwing is NOT a transport failure** and must keep the
   existing behaviour: pending is cleared and the error is rethrown. The existing
   tests asserting this must keep passing unchanged. Distinguish the two by where
   the throw originated (for example, invoke handler callbacks inside their own
   try/catch and tag or rethrow distinctly) — do not distinguish by inspecting
   error message text.

5. `resumeIfInterrupted(conversationId, handlers?: GenerationHandlers)` is added to
   the `SessionCoordinator` interface and implementation, returning
   `Promise<ResumeResult>` where:

   ```ts
   export interface ResumeResult {
     resumed: boolean;              // false when there was nothing to resume
     generationId: string | null;
     text: string;                  // partialText + deltas received on this resume
     status: "complete" | "error" | "cancelled" | null;
     telemetry: Telemetry | null;
     errorCode: string | null;
     reconciledFromSession: boolean; // true when the seq_not_available fallback ran
     seqs: number[];                // seqs observed on THIS connection, in order
   }
   ```

   Behaviour:
   - It reads the conversation through `conversationStore.getConversation(...)`.
     It must rely on nothing held in memory from a previous `send` — every input
     it needs comes from the store.
   - If there is no conversation, no `pending`, or no `sessionId`, it returns
     `{ resumed: false, ... }` with `text: ""`, `status: null`, `seqs: []` and
     makes no HTTP request.
   - Otherwise it calls
     `apiClient.resumeEvents(sessionId, pending.generationId, pending.lastSeq)`
     and consumes the returned events with the same handler dispatch and the same
     terminal-event handling `send` uses. `text` starts at `pending.partialText`
     and grows with each `content` delta. Each event appends its `seq` to `seqs`
     and updates the persisted progress.
   - On reaching a terminal event it clears pending and reconciles the transcript
     (see criterion 7).

6. **`seq_not_available` fallback.** If `resumeEvents` throws a `HarnessApiError`
   with `code === "seq_not_available"`, `resumeIfInterrupted` must NOT propagate
   it. It instead calls `apiClient.getSession(sessionId)`, reconciles from that
   snapshot, clears pending, and returns a result with
   `reconciledFromSession: true` and `status` taken from the matching entry in the
   snapshot's `generations` array (matched on `generation_id === pending.generationId`),
   mapped to `"complete" | "error" | "cancelled"` — the snapshot's `"failed"` maps
   to `"error"`, and a `"queued"`/`"in_flight"` status or a missing entry leaves
   `status: null` with pending left in place, since there is nothing terminal to
   record yet. Any OTHER `HarnessApiError` code propagates to the caller unchanged.

7. **Transcript reconciliation must not duplicate turns.** The service appends both
   the user turn and the assistant turn itself, so `GET /v1/sessions/{id}` is
   authoritative. When `resumeIfInterrupted` reaches a terminal state (either via
   the stream or via the fallback), it reconciles the conversation's local turns
   from the session snapshot's `turns` array rather than appending guessed turns:
   the local `turns` become the snapshot's turns mapped to the local `Turn` shape
   (`{ role, content, cancelled, createdAt }`, with `createdAt` from the snapshot's
   `created_at`), replacing the local list. Running `resumeIfInterrupted` twice in
   a row must not change the transcript the second time, and must not duplicate
   any turn. Add a test proving that idempotence.

8. Every existing test in `test/web/session-coordinator.test.ts` still passes. Do
   not weaken or delete any existing assertion. Add new tests, in the existing
   style, covering criteria 2, 3, 4, 5, 6 and 7 — including at minimum:
   - a mid-stream transport failure leaving pending set with the right lastSeq and
     partialText, read back through a freshly constructed store;
   - a resume driven entirely by a freshly constructed coordinator + store over the
     same storage port, with no carry-over from the interrupted run, producing the
     concatenated full text and the terminal event;
   - the union of seqs across the two connections being contiguous with no
     duplicates;
   - the `seq_not_available` fallback reaching `getSession` and returning
     `reconciledFromSession: true`;
   - a non-`seq_not_available` API error propagating.
