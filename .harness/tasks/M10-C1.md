TASK

Goal:
Make a failing cache write in the service worker's shell handler unable to discard an
already-successful network response.

Relevant Requirements:
Correction for the second IMPORTANT finding in `.harness/reviews/M10-cycle1.md`
("A failed cache write discards a successful network response"). Read that finding in the
report — it states the problem, the reproduction and the suggested correction. Do not read
the rest of the report.

M10's third acceptance criterion (derived: FR2) is that the service worker uses a
network-first strategy for the shell: after the bundle is rebuilt, a fetch through the
worker's strategy returns the NEW build, not the cached one. The defect below silently
violates exactly that criterion whenever the cache write fails.

Background: in `web/src/sw.ts:46-75`, `handleShellRequest` awaits `deps.cachePut` at line 52
INSIDE the same `try` whose `catch` at line 65 is the offline fallback. So if the cache
write rejects (e.g. `QuotaExceededError` under iOS storage pressure), a 200 response already
in hand is thrown away: with a warm cache the handler silently returns the STALE build, and
with an empty cache it rethrows and the document fails to load entirely.
