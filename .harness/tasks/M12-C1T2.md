TASK

Tier: Mid. Reason: **not low risk, and cross-module.** The change threads a new
field through view-model -> mount -> dom-target -> main.ts, and it is the FR9
error-surfacing path that M12 discarded. Getting the error-to-message mapping
wrong reproduces the exact failure this cycle exists to fix: a user who cannot
tell working from broken.

Goal:
Fix BLOCKER 2 of `.harness/reviews/M12-cycle1.md` (read that finding in full --
do not work from this summary alone). Every failure path in the interactive
layer is currently silent: swallowed rejections and bare guard `return`s. Make
failures and refusals reach the screen.

Relevant Requirements:
FR9 -- documented error codes must be "surfaced meaningfully rather than as a
generic failure", and `unauthorized` specifically must "prompt to re-pair". M7
built that guidance surface (`ErrorGuidance`, `httpErrorGuidance`,
`streamErrorGuidance`, `HarnessHttpError.guidance`, `HarnessStreamError.guidance`
in `web/src/api-client.ts`); the interactive layer added in M12 discards it
before it can reach the screen.

Context you need: the harness returns **401** to an unauthenticated request, so
on an unpaired phone `coordinator.listProfiles()` rejects, `main.ts` swallows it,
the `<select>` stays empty, and `Create` then hits `if (!selectedProfileId)
return;` and is a silent no-op too. That is what the human saw.

The mechanism is decided. Implement it; do not redesign it.

  A. `web/src/ui/view-model.ts`
     - Add `notice: string | null` to `UiState` and to `ViewModel`.
     - `buildViewModel` passes it straight through.
     - Add and export a DOM-free helper:
           export function describeError(error: unknown): string
       It must use the existing guidance surface rather than inventing text:
       if the error carries a `guidance` object (HarnessHttpError,
       HarnessStreamError, and the offline/other error classes in
       api-client.ts all do), build the message from that guidance -- read
       `ErrorGuidance`'s fields and use them; include the error `code`.
       For code `unauthorized` the message must explicitly say the phone is not
       paired (or the pairing is no longer valid) and prompt the user to scan
       the QR code again to re-pair. Fall back to a readable message for an
       unrecognised error rather than "[object Object]" or an empty string.

  B. `web/src/ui/mount.ts`  (must stay DOM-free -- it must never runtime-import
     ./dom-target; see the "no bypass access" suite in test/web/ui/mount.test.ts)
     - `notice` in the initial state (`initialState?.notice ?? null`), and in
       `copyState`.
     - Add `setNotice(notice: string | null): void` to `MountHandle`: sets state,
       then `paint()`.

  C. `web/src/ui/dom-target.ts`
     - Add `setNotice(notice: string | null): void` to the `DomController`
       interface.
     - Create a `noticeSection` with `data-testid="notice"` and append it **LAST**
       in `root.replaceChildren(...)`, after `statusSection`. Appending last is
       required: several tests select positionally (`sections[2]`,
       `querySelectorAll("ul")[1]`), and adding a section at the end with no
       `<ul>` inside it leaves every existing index valid. Do not reorder or
       insert anywhere else.
     - `paint()` sets `noticeSection.textContent = view.notice ?? ""`.
     - Replace the send handler's `.catch(() => {})` (~line 143) with one that
       calls `d.controller.setNotice(describeError(error))`. Also clear the
       stale streaming text.
     - Replace the create handler's `.catch(() => {})` (added by the previous
       correction task, with a comment pointing here) the same way.
     - Clear the notice at the start of an action that is actually proceeding,
       so a stale message does not sit under a working app.
     - **Every guard clause that declines to act must say why**, via
       `setNotice`, in these handlers:
         send   -- no conversation selected; empty prompt text
         cancel -- no conversation selected
         profile-change -- no conversation selected
         create -- no profile selected. This is the unpaired case the human hit,
                   so the message must point at pairing, not just say "pick a
                   profile".
       The `if (!deps) return;` guard is the only one that may stay silent --
       there is no controller to speak through before `attach()`. Leave it, and
       say so in your return.

  D. `web/src/main.ts`
     - Replace `coordinator.listProfiles().then(...).catch(() => {})` (~line 103)
       with a `.catch` that calls `handle.setNotice(describeError(error))`.
       Delete the now-false comment claiming "error surfacing is not this
       milestone's scope".
     - It must still be true that a failure here does not stop the app mounting.
     - The service-worker registration `.catch` at ~line 121 is NOT in scope;
       leave it.

Acceptance Criteria:
1. A send that rejects puts a message derived from the error's guidance into
   `[data-testid="notice"]`. Silent failure is gone.
2. A `listProfiles()` rejection during `bootstrap()` puts a message into the
   notice region; a 401 / `unauthorized` message explicitly prompts the user to
   re-pair. `bootstrap()` still returns a mounted handle and does not throw.
3. Clicking Send with no conversation selected, Send with empty text, Cancel with
   no conversation selected, changing the profile with no conversation selected,
   and Create with no profile selected each leave a message explaining why
   nothing happened. None of them is silently inert.
4. `describeError` is unit-tested against a real `HarnessHttpError` with code
   `unauthorized` (constructed from api-client, not hand-rolled) and against at
   least one stream error and one non-Error value.
5. No positional test selector breaks. If one does, fix that selector and
   **report exactly which, and why the document shape had to change** -- that is
   information the next review needs.
6. **Bite-check every assertion you add.** Revert your source change (keep the
   test), run the test, confirm it FAILS; restore, confirm it PASSES. Paste both
   runs' relevant output into your return. An assertion that passes with the
   correction reverted is not evidence.
