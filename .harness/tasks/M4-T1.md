TASK

Goal:
Add a `cancel(conversationId)` method to the Session Coordinator (C9) that cancels the
conversation's in-flight generation via the API Client (C7) and returns the terminal status
the service reports.

Relevant Requirements:
- FR6 (`.harness/requirements.md` line 55-57): "Cancel a running or queued generation and
  reflect the resulting terminal state."
- Agreed architecture interface `C10 -> C9` (`.harness/architecture.md` line 208) already
  names `cancel(conversationId)`. This task realises a method that is already part of the
  agreed design; it is not a new interface.
- Edge case (`.harness/requirements.md` line 145): "Cancelling an already-complete, failed,
  or cancelled generation is idempotent and returns that generation's actual final status."

Acceptance Criteria:
- `SessionCoordinator` gains `cancel(conversationId: string): Promise<{ status: string }>`,
  declared on the exported `SessionCoordinator` interface and implemented in
  `createSessionCoordinator`.
- It reads the conversation via `conversationStore.getConversation(conversationId)`.
  - If the conversation does not exist, it throws `Error` with message
    `Conversation not found: <conversationId>` (match the existing wording used by `send`).
- It determines the generation to cancel from the conversation's `pending` field
  (type `PendingGeneration`, already on `Conversation`) and the conversation's `sessionId`.
  - If `pending` is null, or `sessionId` is null, there is nothing in flight: throw `Error`
    with message `No generation in flight for conversation: <conversationId>`.
- When both are present it calls
  `apiClient.cancel(conversation.sessionId, conversation.pending.generationId)` exactly once
  and returns that call's result unchanged (i.e. `{ status }` as the service reported it).
  Do NOT coerce, validate, or rewrite the status string — returning the service's actual
  final status verbatim is the point of the idempotency requirement.
- Errors from `apiClient.cancel` (e.g. `HarnessApiError`) propagate to the caller unchanged.
- `cancel` does NOT itself mutate the conversation store. The in-flight `send` loop observes
  the resulting `cancelled` SSE event and owns the resulting bookkeeping. Cancelling must not
  race with, or duplicate, that.
