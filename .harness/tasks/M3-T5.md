LIVE FACTS established during planning — design to these, they are measured, not guessed:
- The three live profiles are discovered at runtime. Do NOT write any of their ids into the
  script; a repository-wide guard test (`test/no-hardcoded-profile-ids.test.ts`) will fail the
  build if you do.
- One profile has `latency_class: "interactive"`; the other two are `"batch"`.
- The service runs ONE generation at a time globally. A second admitted generation is `queued`.
- The reverse proxy closes an idle SSE connection after roughly 12 seconds. A generation that
  queues, or whose model load is slow, therefore has its stream closed with NO terminal event.
  When that happens the Session Coordinator throws `Stream ended without terminal event`.
  This is expected and must be handled, not allowed to crash the run.
- Because of that, do NOT assume every profile can be carried to `complete`. One batch profile
  in particular reliably fails to complete on a single connection.
- An admitted generation that is never cancelled keeps holding the single global slot and will
  jam every later step. Everything you admit, you must release.

Required structure — four phases, run STRICTLY SEQUENTIALLY so nothing ever queues:

PHASE 1 — discovery (criteria 1 and 2)
- Call `listProfiles()`. Print every id, role, quality, latency_class and label returned.
- Assert the list is non-empty and has at least 3 entries.
- Every profile id used anywhere later in the script MUST come from this response. The script
  must contain no profile id literal of any kind.

PHASE 2 — every profile is selectable (criterion 1 / AC11)
- For EACH profile in the runtime list, in sequence:
  - create a fresh session via `createSession()`;
  - call `generate()` with that profile id and a short prompt;
  - assert it was admitted: a non-empty `generationId` came back (this is the `x-generation-id`
    header, and only a 200 produces one);
  - IMMEDIATELY call `apiClient.cancel(sessionId, generationId)` and assert the returned status
    is a terminal one. Releasing the slot is mandatory — do not skip it on any path, including
    when an assertion fails. Use try/finally.
- Assert that the number of profiles proven admitted equals the number returned in Phase 1.
  Print the count. This is what makes "all three selectable" true rather than asserted.

PHASE 3 — changing the profile changes the generation (criterion 3)
- Choose profile A: the first with `latency_class === "interactive"`, else the first in the list.
- Create ONE conversation via the conversation store, with profile A.
- `send()` a short prompt. Assert it reaches status `complete` and that
  `telemetry.profile_id === A.id`. Print both.
- Then choose profile B: iterate the remaining profiles in list order and, for each, call the
  store's `setProfileId(conversationId, B.id)` and `send()` a short prompt on the SAME
  conversation. The first one that reaches status `complete` becomes B.
  - A profile that fails to complete (the ~12s stream close described above) is not a proof
    failure at this step; log it, move to the next candidate. But if such a generation was
    admitted, make sure it is released before continuing.
- Assert a B was found, that `B.id !== A.id`, and that its `telemetry.profile_id === B.id`.
- Assert the conversation's stored `profileId` is B.id at the end.
- Print A.id, B.id and both observed `telemetry.profile_id` values. The whole point is that
  the SERVICE's own telemetry, not the client's claim, confirms which profile ran.

PHASE 4 — unknown profile is a typed error (criterion 4)
- Build an id guaranteed not to exist, e.g. `"unknown-profile-" + crypto.randomUUID()`.
- Assert it is genuinely absent from the Phase 1 list before using it.
- Create a session, call `generate()` with it, and assert it throws `HarnessApiError` with
  `code === "unknown_profile"` and `status === 400`.
- Assert specifically that the code is NOT the generic `http_400` fallback. That distinction is
  the criterion.
