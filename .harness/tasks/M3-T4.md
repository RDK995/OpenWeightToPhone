TASK

Goal:
Add a standing test that fails if any live profile id literal ever appears in shipped source,
so milestone M3's "no hardcoded profile ids" criterion is enforced continuously rather than
proven once by hand.

Tier: Cheap. Routing reason: none — the rule is stated exactly, the blast radius is one new
test file, and it is settled by `bun test`.

Relevant Requirements:
- FR5 (Profiles): "Fetch `/v1/profiles` at runtime. Profile ids are never hardcoded."
- Milestone M3 criterion: "No profile id literal appears in shipped source; the selectable set
  is derived solely from the runtime `/v1/profiles` response."

Acceptance Criteria:
- A new test file `test/no-hardcoded-profile-ids.test.ts` scans every `.ts` file under
  `web/src/`, `src/` and `scripts/` (recursively) and asserts none of them contains any of the
  three live profile id strings: `reasoning-baseline`, `reasoning-capable`, `reasoning-deep`.
- The scan is driven by reading the filesystem at test time, not by a hand-written list of file
  paths — adding a new source file later must be covered automatically. Use Bun's filesystem
  APIs or `node:fs` as the repository already does elsewhere.
- The failure message names the offending file and the literal found, so a future failure is
  actionable rather than a bare boolean.
- The test asserts it actually scanned a non-zero number of files, and that the count is at
  least 8. Without this, a broken glob would make the test pass vacuously — which is the main
  way a guard like this rots. This assertion is mandatory.
- Test files themselves are deliberately NOT scanned: the literals legitimately appear in this
  guard test and in the milestone record. Only shipped source is in scope.
- Prove the guard actually bites: temporarily insert one of the literals into a scanned source
  file, confirm the test goes red and names that file, then remove it and confirm green again.
  Report both observed outcomes in your return. Leave the file byte-identical to how you found
  it — verify with `md5` before and after and report both hashes.

Relevant Files:
- `test/build.test.ts` — read this first for the repository's existing pattern for a test that
  inspects files on disk; follow its style.

Files Allowed To Change:
- `test/no-hardcoded-profile-ids.test.ts` (new file only)

Constraints:
- Create no other file. Change no source file permanently.
- Follow existing repository patterns.
- Do not introduce dependencies.
- Do not weaken tests.
- Do not add a `typecheck` script or otherwise widen scope.

Tests:
export PATH="$HOME/.bun/bin:$PATH" && bun test test/no-hardcoded-profile-ids.test.ts

Return:
