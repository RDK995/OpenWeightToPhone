Reason for going above Cheap: **cross-cutting**. This component is the integration seam
between the API client (C7) and the conversation store (C8), and it owns the milestone's
central property — that assistant output is surfaced *as deltas arrive* rather than
buffered. That property has no trivial local test oracle: a naive implementation that
collects the whole stream and then reports it passes every naive test. The test design here
is the substance of the task.

Goal:
Implement C9 — Session Coordinator, limited to what this milestone needs: driving one
generation's lifecycle from prompt to terminal event, streaming deltas out incrementally,
and mirroring the resulting turns into the local conversation store.

**Scope limit, deliberate:** implement ONLY `send`. Do NOT implement `cancel` (milestone
M4), `resumeIfInterrupted` (M5), or session rebuild-and-replay on `unknown_session` (M6).
Do not implement profile selection UI concerns (M3). Those are later milestones.

Acceptance Criteria:
- `web/src/session-coordinator.ts` exports
  `createSessionCoordinator(deps: { apiClient: ApiClient; conversationStore: ConversationStore }): SessionCoordinator`,
  importing those types from `./api-client` and `./conversation-store`.
- It exports a `GenerationHandlers` type with these optional callbacks:
  `onQueued(position: number)`, `onModelLoading()`, `onDelta(delta: string)`,
  `onComplete(telemetry: Telemetry)`, `onError(code: string)`, `onCancelled()`.
  `Telemetry` is imported as a type from `./sse-reader`.
- `send(conversationId: string, prompt: string, handlers?: GenerationHandlers): Promise<SendResult>`
  where `SendResult` is `{ generationId: string; text: string; status: "complete" | "error" | "cancelled"; telemetry: Telemetry | null; errorCode: string | null }`.
- **Behaviour of `send`, in order:**
  1. Rejects an empty or whitespace-only prompt by throwing, before any request is made.
  2. Throws for an unknown `conversationId`.
  3. If the conversation has no `sessionId`, calls `apiClient.createSession()` and persists
     the id via the conversation store before generating. If it already has one, reuses it —
     this reuse is what gives the model context across prompts.
  4. Calls `apiClient.generate(sessionId, { profileId: conversation.profileId, prompt })`.
  5. Records the in-flight generation via `conversationStore.recordProgress(conversationId,
     { generationId, lastSeq: -1, status: "in_flight" })` before consuming the stream, and
     updates `lastSeq` from each event's `seq` as events arrive. (`-1` matches the API's own
     "-1 if nothing emitted".)
  6. Iterates the event stream and dispatches each event to the matching handler **as it
     arrives**, accumulating `content` deltas into the returned `text`.
  7. On the terminal event, clears `pending` via `recordProgress(conversationId, null)` and
     mirrors the turns locally: appends a user turn with the prompt and, for a `complete`,
     an assistant turn with the accumulated text — both with `cancelled: false`. For an
     `error` terminal event, append the user turn only. Local turns are a mirror of the
     service's state (architecture: "A local mirror of the service's turns"); they are
     written **locally only**.
  8. Resolves with the `SendResult`.
- **The coordinator makes no `POST /v1/sessions/{id}/turns` call, ever.** Mirroring is to
  the local `conversationStore`, never to the API. There must be no call to any api-client
  method that appends turns (the client has none in this milestone, and you must not add
  one).
- **Incrementality is enforced by the test, not merely asserted.** Write a test using a fake
  api-client whose event stream is an async generator that yields a `content` delta, then
  *waits on a promise the test controls* before yielding the next. The test must prove that
  `onDelta` was already invoked with the first delta **while the stream is still open** —
  i.e. before the second delta is released and before `send`'s promise resolves. A buffered
  implementation must fail this test. This is the milestone's central acceptance criterion;
  a test that only checks the final accumulated text is not sufficient and does not satisfy
  this criterion.
- `onQueued` receives the 1-based `position` from a `queued` event; `onModelLoading` is
  invoked for a `model-loading` event; `onComplete` receives the telemetry object from the
  `complete` event; `onError` receives the `error` code string; `onCancelled` is invoked for
  a `cancelled` event.
- A handler throwing must not corrupt coordinator state or leave `pending` set forever. Decide
  and test one honest behaviour (either the error propagates after `pending` is cleared, or
  handler errors are swallowed) and document it in a comment.
- If the stream ends with no terminal event, `send` rejects with a clear error and `pending`
  is cleared.
- Missing handlers are fine — every callback is optional and absent ones are simply not called.

Tier: Cheap

Finding: verification confirmed the decisive incrementality criterion is genuinely proven (a
buffering implementation makes the test time out). But one criterion is only partially
covered: "Records the in-flight generation ... and updates `lastSeq` from each event's `seq`
as events arrive." The suite tests the INITIAL `recordProgress` call (`lastSeq: -1`,
`status: "in_flight"`) and the FINAL clear to `null`, but nothing asserts that `lastSeq`
actually advances per event in between.

Why this matters beyond tidiness: `lastSeq` is the resumption cursor. Milestone M5 resumes an
interrupted generation with `GET /v1/generations/{id}/events?after_seq=<lastSeq>`. If
`lastSeq` silently stayed at `-1`, every test here would still pass, and the defect would only
surface in M5 as replayed or lost tokens. Pin the behaviour now, where it is cheap.

Goal: add test coverage for the per-event `lastSeq` advance. Implementation change only if the
tests reveal it is actually wrong.

  inspecting only the final state).
