Acceptance Criteria:
- New file `web/public/app.webmanifest` containing exactly this JSON (formatted with two-space
  indent, trailing newline):
    {
      "name": "Phone Reasoning Surface",
      "short_name": "Reasoning",
      "id": "/app/",
      "start_url": "/app/",
      "scope": "/app/",
      "display": "standalone",
      "orientation": "portrait",
      "background_color": "#111111",
      "theme_color": "#111111",
      "icons": [
        { "src": "/app/icons/icon-192.png", "sizes": "192x192", "type": "image/png", "purpose": "any" },
        { "src": "/app/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any" },
        { "src": "/app/icons/apple-touch-icon-180.png", "sizes": "180x180", "type": "image/png", "purpose": "any" }
      ]
    }
  The icon `src` values are absolute paths under the mount, so they resolve identically
  whether the manifest is fetched as `/app/app.webmanifest` or from a nested path.
  `src/host/pwa-server.ts` already maps the `.webmanifest` extension to
  `application/manifest+json` — do not change that.
- `web/public/index.html` gains, inside `<head>` and without disturbing the existing
  charset, viewport, title, style or the `<script type="module" src="./main.js">`:
    <link rel="manifest" href="./app.webmanifest">
    <link rel="apple-touch-icon" sizes="180x180" href="./icons/apple-touch-icon-180.png">
    <meta name="apple-mobile-web-app-capable" content="yes">
    <meta name="mobile-web-app-capable" content="yes">
    <meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">
    <meta name="apple-mobile-web-app-title" content="Reasoning">
    <meta name="theme-color" content="#111111">
  Keep the file's existing tab indentation. The two `*-web-app-capable` metas are both
  required: older iOS honours the `apple-` prefixed one, and it is what makes the launched
  app chrome-less rather than opening in Safari.
- New test file `test/web/manifest.test.ts` (Bun test, `import { describe, it, expect } from "bun:test"`,
  matching the conventions of the neighbouring tests under `test/web/`) that:
    * reads `web/public/app.webmanifest` from disk and `JSON.parse`s it, asserting the parse
      succeeds (a manifest that does not parse makes the app uninstallable and is the single
      most likely way this milestone silently fails);
    * asserts `display === "standalone"`;
    * asserts `start_url` is a string that starts with `/app/`, and likewise `scope`;
    * asserts `icons` is a non-empty array and that EVERY entry has `src`, `sizes`, `type`
      and that `type` starts with `image/`;
    * asserts, for EVERY icon entry, that the file it names actually exists on disk: map
      `src` from `/app/<rest>` to `web/public/<rest>` and assert `existsSync` is true and
      the file is non-empty. This is the on-disk half of the acceptance criterion — the
      served half is proven separately by the milestone proof script;
    * asserts each icon file's real pixel dimensions parsed from its PNG IHDR match the
      `sizes` string it declares (read bytes 16..24 of the PNG for width and height — do not
      trust the filename);
    * reads `web/public/index.html` and asserts it contains a `rel="manifest"` link whose
      href resolves to the manifest, an `apple-touch-icon` link, and both
      `apple-mobile-web-app-capable` and `mobile-web-app-capable` metas with content "yes";
    * asserts the existing `<script type="module" src="./main.js">` tag is still present, so
      this change cannot silently break the bundle entry point.
- After `bun run build`, `web/dist/app.webmanifest` and `web/dist/icons/*.png` must exist
  (the build copies `web/public/` verbatim, so this should need no build change — confirm
  it, and if it does NOT hold, report that in Unresolved Issues rather than editing
