  ### GET /v1/sessions/{session_id}/generations/{generation_id}/events
  Query parameters:
  - `from_seq` (optional, integer): Resume after this sequence number. `-1` means
    send everything.
  Request headers:
  - `Last-Event-ID` (optional): Takes precedence over `from_seq`.
  Response: 200 OK (streaming). Server-Sent Events with the same wire format as
  `/generate`. You receive all events with `seq > afterSeq`.
  Response header: `x-generation-id` contains the generation id.
  Failures:
  - `401 unauthorized`
  - `400 invalid_request` — Resume point is malformed or less than -1
  - `404 unknown_session`
  - `404 unknown_generation`
  - `409 seq_not_available` — Requested sequence number is no longer available.
    The response includes `last_seq`:
    {"api_version": "v1", "error": "seq_not_available", "last_seq": 42}

Acceptance Criteria:
1. `ApiClient` gains `resumeEvents(sessionId: string, generationId: string,
   lastSeq: number, options?: { signal?: AbortSignal }):
   Promise<{ generationId: string; events: AsyncIterable<HarnessEvent> }>`.
   It issues `GET /v1/sessions/{sessionId}/generations/{generationId}/events`
   with the header `Last-Event-ID: <lastSeq>` and returns the parsed event
   iterable via the existing `readEvents(response.body)`, exactly as `generate`
   does. The returned `generationId` comes from the `x-generation-id` response
   header; if that header is absent, fall back to the `generationId` argument
   rather than throwing (the caller already knows which generation it asked for).
2. A `409` response whose body carries `"error": "seq_not_available"` surfaces as
   a thrown `HarnessApiError` with `code === "seq_not_available"`, `status === 409`,
   and `body` retaining the parsed JSON including its `last_seq` field. This must
   fall out of the existing `handleResponse` error mapping — do not add a special
   case for it. Add a test proving it.
3. `generate` and `resumeEvents` both accept an optional
   `options.signal` / third-argument `signal` (an `AbortSignal`) that is passed
   through to the underlying `fetch` call, so an in-flight stream can be aborted
   by the caller. `generate`'s existing signature
   `generate(sessionId, { profileId, prompt })` must keep working unchanged for
   existing callers; add `signal` as an optional extra field of that same options
   object. Do not change any other method's signature.
4. Aborting the signal while the stream is being consumed causes the underlying
   fetch/stream to reject or terminate rather than hanging. Prove this with a test
   using a stub fetch that respects the signal.
5. Every existing test in `test/web/api-client.test.ts` still passes unchanged.
   Do not weaken or delete any existing assertion.
