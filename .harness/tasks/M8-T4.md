TASK

Goal:
Make creating a conversation provision exactly one server session for it, so that a
conversation is backed by exactly one server session id from the moment it exists —
rather than lazily acquiring one on first send.

Tier: Mid. Reason: not low risk — this changes the session lifecycle that M6's
session-loss recovery already depends on, so a wrong change breaks proven behaviour.

Relevant Requirements:
- FR3 — "Each conversation is backed by exactly one server session."
- Architecture C9 (Session Coordinator: "Drive a generation's lifecycle"; Depends on
  C7 API Client, C8 Conversation Store), C8 (Conversation Store; Depends on C11 ONLY).

Acceptance Criteria (this is milestone M8's AC2):
- The Session Coordinator gains a conversation-creation entry point (e.g.
  `createConversation(input: { profileId: string; title?: string }): Promise<Conversation>`)
  added to the exported `SessionCoordinator` interface. It must:
  1. create the conversation in the conversation store, AND
  2. call `apiClient.createSession()` EXACTLY ONCE, AND
  3. record the returned session id on the conversation via
     `conversationStore.setSessionId(...)`, AND
  4. return the conversation with its `sessionId` populated (not null).
- Exactly one session per creation: creating one conversation must result in exactly one
  `createSession` call. Prove this with a test that counts calls on a stubbed api client.
- The conversation's session id is then STABLE: a subsequent `send()` on that
  conversation must NOT create another session. `send()` already skips creation when
  `conversation.sessionId` is set (see the `if (!sessionId)` guard) — verify this holds
  and cover it with a test asserting `createSession` was called exactly once across
  create-then-send.
- ARCHITECTURAL BOUNDARY, do not violate it: C8 (`conversation-store.ts`) depends on C11
  ONLY. The store must NOT import, call, or know about the api client. All session
  provisioning lives in C9 (`session-coordinator.ts`). The store's own
  `createConversation` keeps its current signature and keeps setting `sessionId: null`.
- M6's session-loss recovery MUST remain intact: when `generate()` fails with an unknown
  session (the existing 404 rebuild path around lines 277-282 of
  `session-coordinator.ts`), the coordinator still creates a replacement session and
  replays the transcript. "Exactly one session id at a time" is the invariant — a
  conversation whose session was LOST is still allowed to acquire a replacement. Do not
  break, and do not delete, the existing rebuild path or its tests.
- `send()`'s existing lazy-creation guard stays as a fallback for conversations created
  directly through the store (M2-M7 proofs do this). Do not remove it.
