Tier: Mid.
Named reason: **not low risk**. This script is the only evidence M5's criteria
hold — every acceptance criterion is proven here or not at all. The dangerous failure
is not a crash, it is a proof that passes *vacuously*: aborting after the terminal
event has already arrived, or "resuming" a generation that had already finished,
both produce a green run that proves nothing. Timing against a live model is
genuinely fiddly, and a vacuous pass is exactly the kind of wrong that nothing
downstream will catch.

Goal:
Write `src/host/m5-proof.ts`, a Mac-run entry point that proves all four of M5's
acceptance criteria against the LIVE harness, and register it as `proof:m5` in
`package.json`.

Relevant Requirements:
FR7 — "On reconnect or return to foreground, resume the event stream via
`GET /v1/sessions/{id}/generations/{id}/events` using `Last-Event-ID` set to the
last received seq, yielding no gaps and no duplicates. Disconnecting is
distinguished from cancelling: a dropped connection leaves the generation running."

Requirements edge case — "`409 seq_not_available` on resume — the buffer has
discarded the requested seq; fall back to fetching the session and reconciling
from its recorded state."

The four M5 acceptance criteria this script must prove, quoted from
`.harness/milestones.md`:

  - **AC7** — Killing the connection mid-stream and resuming with `Last-Event-ID`
    yields no gaps, no duplicates, and delivers the terminal event. Proven live.
  - (derived: FR7) A dropped connection leaves the generation running — its status
    read from `GET /v1/sessions/{session_id}` after the drop and before the resume
    is `queued` or `in_flight`, not `cancelled`. Proven live.
  - (derived: FR7) A resume succeeds from a coordinator constructed fresh from
    persisted storage alone, with no in-memory carry-over from the interrupted run.
  - (derived: edge case) A resume point older than the service's buffer surfaces
    `seq_not_available` (`409`) as its own typed error, and the client falls back to
    reconciling from `GET /v1/sessions/{session_id}` rather than failing.

Acceptance Criteria:

1. `src/host/m5-proof.ts` exists and follows the established proof-script pattern.
   **Read `src/host/m4-proof.ts` in full first and follow its structure**: read
   config via `resolveBaseUrl()` / `readToken()` from `./config.ts`, build the
   module chain (`createMemoryStorage` -> `createCredentialStore` ->
   `createApiClient` -> `createConversationStore` -> `createSessionCoordinator`),
   print clearly-labelled numbered steps, and `main().catch(...)` at the end with a
   non-zero exit on failure.

2. It exercises the architected path C10 -> C9 -> C7. Drive the coordinator's
   public methods (`send`, `resumeIfInterrupted`); do not reach past C9 into the
   api-client to do the work C9 exists to do. A direct C7 call is acceptable ONLY
   for the out-of-band status read in criterion 4 and the deliberate bad-resume
   probe in criterion 7, and each such call must carry a comment saying why.

3. **The drop is a real transport kill, mid-stream.** Start a generation with a
   prompt long enough to produce a genuine run of `content` events (see
   `LONG_PROMPT` in `m4-proof.ts` for the established shape). Pass an
   `AbortController`'s signal into the generation, and abort it only AFTER at least
   3 `content` deltas have actually been observed, and BEFORE any terminal event.
   Assert both of those facts explicitly and fail loudly if the abort could not be
   performed mid-stream — for example if the generation completed before 3 deltas
   arrived. **A run that could not abort mid-stream must FAIL, not pass with a
   warning.** This is the vacuity guard and it is the most important line in the
   script.

4. **Between the drop and the resume**, read the generation's status directly via
   `apiClient.getSession(sessionId)` and assert the matching generation's `status`
   is `"queued"` or `"in_flight"` — explicitly NOT `"cancelled"` and not
   `"complete"`. Print the observed status. This is the criterion that a dropped
   connection does not cancel the work.

5. **The resume runs from a genuinely fresh coordinator.** Construct a NEW
   `ConversationStore` and a NEW `SessionCoordinator` over the SAME `StoragePort`
   instance, and call `resumeIfInterrupted(conversationId)` on the new coordinator.
   Nothing from the interrupted run may be carried over in memory — no reuse of the
   first store, the first coordinator, or any local variable holding the partial
   text or last seq. Print which objects are fresh. The partial text must come back
   out of persisted storage, not from a variable.

6. **Prove the seq union.** Collect the seqs observed on the first connection and
   the seqs returned in `ResumeResult.seqs` from the resumed connection. Assert
   that their union, sorted, is exactly the contiguous run `[0, 1, ..., N]` with no
   gaps, that every seq appears exactly once (`new Set(all).size === all.length`),
   and that a terminal event was delivered on the resumed connection. Print the two
   seq ranges and the union's bounds. If the harness's first seq turns out not to
   be 0, assert contiguity from whatever the observed minimum is and print it —
   contiguity and uniqueness are the criterion, the specific starting number is not.

7. **Prove the `seq_not_available` fallback live.** On a SECOND, separate
   generation that you allow to run to completion, attempt a resume from a seq the
   service cannot honour and assert the live service returns `409`
   `seq_not_available`. The reliable way to provoke this against the real service
   is a resume point ABOVE the generation's `last_seq`: the harness returns
   `seq_not_available` when `afterSeq > lastSeqOf(record)`
   (`harness/api/generation.ts`), so resuming with `last_seq + 1000` produces a
   genuine live 409. Assert the thrown error is a `HarnessApiError` with
   `code === "seq_not_available"` and `status === 409`. Then prove the client's
   fallback: arrange the conversation's persisted `pending` to carry that
   unreachable `lastSeq`, call `resumeIfInterrupted`, and assert it did NOT throw,
   that the returned `reconciledFromSession === true`, and that the transcript was
   reconciled from the session snapshot. Print the recovered status.

8. `package.json` gains `"proof:m5": "bun run src/host/m5-proof.ts"` alongside the

Operational notes:
- The service runs ONE generation at a time globally and admits at most one per
  session. If you leave a generation running, later runs and other work will block
  on `409 generation_in_flight` or `503 queue_full`. **Always cancel or drain any
  generation this script started**, including on the failure path — `m4-proof.ts`
  has an established `lastAdmitted` safety-net wrapper around `generate` for
  exactly this; reuse that idea.
- Use the `reasoning-baseline` profile for speed, but **discover it from
  `listProfiles()` rather than hardcoding the id** — FR5 forbids hardcoded profile
  ids and there is a test (`test/no-hardcoded-profile-ids.test.ts`) enforcing it.
  Read that test before you write the script so you do not trip it.
- The generation wall-clock budget is 300s. Keep prompts modest.
