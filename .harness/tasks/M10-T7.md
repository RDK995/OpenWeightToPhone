Solution space — what you MAY change inside C13:
Everything here is an implementation detail of the property list. None of it alters the
agreed `C13 -> C4` interface, so none of it needs architecture agreement.
- **`KeepAlive` as a dict** rather than unconditional `<true/>` — e.g.
  `{ SuccessfulExit = false }`, `{ Crashed = true }`, or both (dict keys are OR-ed).
  M10-T6's packet forbade this; **that prohibition is lifted for this attempt**, because
  the dict is a different launchd code path and is now one of the strongest candidates.
  **But**: C13's responsibility is to restart the server *if it exits*, unqualified. If you
  ship a dict, state explicitly in your return which exit classes it covers and which it
  does not, so the orchestrator can judge it against that responsibility. A dict that
  cannot restart after SIGKILL fails the criterion outright.
- **`StartInterval`** (e.g. 10) as a demand-spawn safety net. This is worth serious
  consideration: launchd is deferring a *nondemand* spawn, and a `StartInterval` tick is a
  *demand* spawn, so it may sidestep the deferral entirely. It adds a key without removing
  `KeepAlive` or `RunAtLoad`, requires **no change whatsoever to C4**, and bounds worst-case
  recovery to the interval. If you use it, keep the interval comfortably inside the 45s
  window and say so.
- `ThrottleInterval`, `ExitTimeOut`, `LimitLoadToSessionType`, `AbandonProcessGroup`,
  `Nice`, `LowPriorityIO`, `EnableTransactions`, and any `ProcessType` value or its
  absence. (`ProcessType` alone is already falsified, but it may matter in combination.)

  precedes `bootstrap`, or whether an additional idempotent verb is needed — as long as the
