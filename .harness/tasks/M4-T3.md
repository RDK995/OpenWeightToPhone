## Acceptance Criteria for this task

The script must prove, live, and print an explicit per-criterion PASS/FAIL line for each:

### Criterion 1 — AC6: cancel mid-generation returns `cancelled` and output stops

- Create a conversation with a profile id **fetched at runtime** from
  `apiClient.listProfiles()`. Never hardcode a profile id (see "Hard constraints").
- Use a prompt long enough to generate a stream of content events (so there is something to
  cancel mid-way). Something like asking for a few sentences of prose is fine — but see the
  cold-model warning below.
- Call `sessionCoordinator.send(...)` with an `onDelta` handler. **Cancel only after at
  least one `content` event has arrived**, so this is genuinely a mid-generation cancel and
  not a cancel of a queued generation. Guard with a flag so cancel is issued exactly once.
- The cancel MUST go through **`sessionCoordinator.cancel(conversationId)`** (the C9 method
  added by M4-T1), not `apiClient.cancel` directly, so the proof exercises the architected
  C10 -> C9 -> C7 path.
- **Mechanical subtlety you must handle:** `onDelta` is a *synchronous* callback
  (`(delta: string) => void`) but `cancel` is async, and `cancel` requires the
  conversation's `pending` record which `send` writes before consuming the stream and clears
  on the terminal path. So the cancel must be *initiated* from inside `onDelta` while `send`
  is still in flight — store the returned promise in an outer variable, and `await` it after
  `send` resolves. Do not `await` inside `onDelta` and do not swallow its rejection.
- Assert:
  - `sessionCoordinator.cancel(...)` resolved to status `cancelled`;
  - the `SendResult.status` is `"cancelled"` (i.e. the stream's terminal event was
    `cancelled`);
  - **output stopped**: count `content` deltas, record the count at the moment cancel was
    issued and the final count, and assert no unbounded continuation — specifically assert
    that the stream terminated with `cancelled` and that no `content` delta arrived *after*
    the terminal `cancelled` event. Track this with a flag set in the coordinator's
    `onCancelled` handler and assert `onDelta` was never invoked after it.
- Print the deltas-before-cancel count, the final delta count, the cancel status and the
  send status in the output, so a reviewer can see the proof rather than only its verdict.
- **Keep the conversation, its id, its `sessionId` and the partial text** — Criterion 3
  needs them.

### Criterion 2 — (derived: FR6, edge case) idempotent cancel returns the ACTUAL final status

This is the criterion that is easiest to get wrong, and it is the reason the task is routed
Mid. The weak half of idempotency (re-cancelling an already-`cancelled` generation) is
already known to return `cancelled`. The proof MUST **also** cover a generation that ran to
**`complete`**:

- Let a generation run to completion (`SendResult.status === "complete"`).
- Then cancel that same, already-complete generation.
- **Assert the call returns `complete`, NOT `cancelled`.** Returning `cancelled` for a
  completed generation would violate "returns that generation's actual final status", and
  this is the only case that can catch it. Do not accept "any terminal status" here; assert
  the exact string `complete`.
- **Mechanical subtlety:** `sessionCoordinator.cancel()` is NOT usable for this. `send`
  calls `conversationStore.recordProgress(conversationId, null)` on the terminal path
  (session-coordinator.ts line ~147), clearing `pending`, so C9's `cancel` would throw
  `No generation in flight for conversation: <id>`. For this case call
  `apiClient.cancel(sessionId, generationId)` directly, using the `generationId` from the
  `SendResult` and the session id from the conversation. Say so in a code comment, so a
  reviewer knows this is deliberate and not a bypass of the architected path.
- Also cover the already-`cancelled` half: re-cancel the Criterion 1 generation (directly
  via `apiClient.cancel`, since its `pending` is likewise cleared) at least twice and assert
  each call returns `cancelled`.
- Print each cancel call's returned status.

### Criterion 3 — (derived: edge case) local transcript agrees with the service

Using the **cancelled** generation from Criterion 1:

- Read the locally stored conversation via `conversationStore.getConversation(id)`. Assert
  it has an assistant turn with `cancelled: true`.
- Call `apiClient.getSession(sessionId)` and find the corresponding assistant turn in
  `snapshot.turns`.
- Assert the local assistant turn's `cancelled` flag **equals** the service turn's
  `cancelled` field (both `true`).
- Also compare the partial **content**: assert the local assistant turn's `content` equals
  the service assistant turn's `content`. If they differ, print both verbatim and FAIL —
  the prior live reconnaissance observed them byte-identical, so a difference is a real
  finding rather than expected noise.
- Print both turns' role, `cancelled` flag and content in the output.

## Hard constraints

1. **Never hardcode a profile id.** `test/no-hardcoded-profile-ids.test.ts` scans every
   `.ts` file under `src/`, `web/src/` and `scripts/` and fails if it finds the literal
   strings `reasoning-baseline`, `reasoning-capable` or `reasoning-deep`. Fetch profiles at
   runtime via `apiClient.listProfiles()` and select by property (e.g.
   `latency_class === "interactive"`) with a fallback to `profiles[0]`, exactly as
   `m3-proof.ts` does.
2. **Cold models and the ~12s proxy idle window.** M3's follow-ups record that a cold model
   plus the proxy's idle window can stall a generation. Criterion 2 needs a generation to
   reach `complete`, which is the most exposed. **Keep that prompt very short** — M3 used
   `"Reply with just the single word 'ready'."`. Reuse that. Only Criterion 1's prompt needs
   to be long enough to yield content events.
3. **Release every generation slot.** The harness admits one generation at a time. Every
   generation the script starts must reach a terminal state before the script exits,
   including on failure paths. `m3-proof.ts` shows the pattern (its `guardedSend` /
   `lastAdmitted` tracking and its `finally` blocks). Adopt an equivalent safety net; a
   proof that leaves a generation in flight will wedge the harness for the next run.
4. **The proof must be genuinely live.** No mock api client, no stubbed transport, no
   fixtures, no recorded responses. It talks to the real service through
   `createApiClient({ baseUrl, getToken })`.
5. **Non-vacuity.** Every criterion must be able to FAIL. Do not write assertions that hold
   regardless of the service's behaviour (e.g. `expect(status).toBeTruthy()`), and do not
   let a criterion print PASS on a path where its evidence was never gathered. If a phase
   could not run, it prints FAIL, not PASS.
6. **Do not weaken or modify any existing test**, and do not modify
   `web/src/session-coordinator.ts` or `test/web/session-coordinator.test.ts` — M4-T1 and
   M4-T2 are complete and accepted.
7. Follow existing project conventions (TypeScript, `.ts` import extensions, the import
   style used by `m3-proof.ts`).
