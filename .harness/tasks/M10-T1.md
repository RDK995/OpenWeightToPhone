TASK

Tier: Cheap (no named reason to go higher: clearly specified, bounded to three new
files plus one test, low risk, and verified by decoding the emitted PNGs).

Goal:
Add a dependency-free PNG icon generator that emits the three home-screen icons the
PWA manifest will name, and commit its output under `web/public/icons/`.

Relevant Requirements:
FR2 (Installation) — "The PWA is installable to the iOS home screen: web app manifest,
icons, and standalone display mode." Component C12 (PWA Shell, `web/public/`).

Acceptance Criteria:
- A new script `scripts/generate-icons.ts` exports
  `export async function generateIcons(options?: { root?: string }): Promise<{ outdir: string; files: string[] }>`
  and, like `scripts/build.ts`, also runs under `if (import.meta.main)` printing the files
  it wrote and exiting 0 on success / non-zero on failure. Resolve `root` from
  `import.meta.url` one directory up, exactly as `scripts/build.ts` does.
- It writes exactly these three files, and returns their paths relative to `outdir`:
    web/public/icons/icon-192.png              192 x 192
    web/public/icons/icon-512.png              512 x 512
    web/public/icons/apple-touch-icon-180.png  180 x 180
- Each file is a real, valid PNG: 8-bit RGB or RGBA, non-interlaced, correct 8-byte PNG
  signature, IHDR with the exact width/height above, valid per-chunk CRC32, and IDAT
  holding a zlib stream. Encode it yourself using `node:zlib`'s `deflateSync` (zlib
  wrapper, which is what PNG requires) and your own CRC32. Add NO npm dependency.
- Apple's home-screen icon is composited on an opaque background, so every pixel must be
  fully opaque: emit color type 2 (truecolour RGB, no alpha) so there is no transparency
  to composite. The artwork itself is your choice but must be deterministic (the same
  bytes on every run) and must not be a single flat colour — draw something simple and
  legible at small size, e.g. a solid dark background (#111111) with a lighter centred
  glyph or shape. No text rendering, no fonts.
- The three files are committed to the working tree (i.e. actually generated and left on
  disk), not produced only at build time. `scripts/build.ts` already copies everything
  under `web/public/` into `web/dist/`, so do NOT modify `scripts/build.ts`.
- A new test file `test/icons.test.ts` (Bun test, `import { describe, it, expect } from "bun:test"`,
  matching the conventions in `test/no-hardcoded-profile-ids.test.ts`) that, for each of
  the three icons:
    * asserts the file exists and is larger than 100 bytes;
    * parses the PNG header itself from the bytes — asserts the 8-byte signature
      `89 50 4E 47 0D 0A 1A 0A`, that the first chunk is `IHDR`, and reads width, height,
      bit depth, colour type and interlace method out of IHDR, asserting the expected
      width/height, bit depth 8, colour type 2, interlace 0;
    * walks every chunk to EOF and asserts each chunk's stored CRC32 equals the CRC32 the
      test recomputes over (chunk type + chunk data), and that the last chunk is `IEND`;
    * asserts at least one `IDAT` chunk is present and that concatenating the IDAT data
      and passing it to `node:zlib`'s `inflateSync` succeeds and yields exactly
      `height * (1 + width * 3)` bytes.
  The test must recompute CRC32 independently in the test file rather than importing the
  generator's CRC helper — the point is to catch a wrong encoder, and sharing the encoder's
  own CRC would defeat that.
- The test also asserts, for at least one icon, that regenerating into a temporary root and
  comparing bytes reproduces the committed file exactly (determinism). Use
  `generateIcons({ root: <tmpdir> })` with `<tmpdir>/web/public/icons` created as needed.
