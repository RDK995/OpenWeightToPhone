Reason for going above Cheap: **no clear local test oracle**. This task produces the
milestone's entire acceptance evidence by driving the LIVE harness API over the network.
There is no fixture to assert against; correctness means the assertions it makes are honest

Goal:
Build the Mac-run CLI entry point that proves this milestone's four acceptance criteria
against the LIVE harness, and run it. It wires the same modules the browser will mount —
storage port, credential store, api client, conversation store, session coordinator — with
the storage port memory-backed, and prints assistant output incrementally as `content`
events arrive.

Relevant Requirements:
- Requirements: "Every criterion is proven against the live harness API, not a mock."
- Milestone M2 Outcome: "A Mac-run entry point, built from the same TypeScript modules the
  browser will load, creates a session against the live harness, sends a prompt, prints
  assistant output incrementally as `content` events arrive, and prints the `complete`
  event's telemetry. It then sends a second prompt in the same conversation and shows the
  model had context from the first."
- Requirements FR4: on `complete`, display telemetry: tokens per second, eval count,
  quantization, and context limit; display queue position while `queued`; display the
  `model-loading` state.

The four acceptance criteria this run must prove, verbatim from the milestone:
- **AC3** — "A prompt produces incrementally rendered tokens, then a `complete` event whose
  telemetry is displayed (tokens per second, eval count, quantization, context limit).
  Proven live."
- **AC4** — "A second prompt in the same conversation demonstrably has context from the
  first. Proven live."
- **AC5** — "Exactly one user turn and one assistant turn are recorded per generation,
  verified via `GET /v1/sessions/{session_id}`. No duplication. Proven live."
- **(derived: FR4)** — "The client issues no `POST /v1/sessions/{id}/turns` at any point
  during a generation — asserted from the client's own record of the requests it made in the
  same live run, not from inspection of the source."

Acceptance Criteria:

A. `src/host/m2-proof.ts` exists and, when run, does the following against the live service:
   1. Reads the base URL with `resolveBaseUrl` and the bearer token with `readToken`, both
      imported from `src/host/config.ts`. Do not hardcode either. Do not reimplement them.
   2. Builds: `createMemoryStorage()` → `createCredentialStore(storage)` (seed it with
      `{ baseUrl, token }`) → `createApiClient({ baseUrl, getToken: () => credentialStore.getToken() })`
      → `createConversationStore(storage)` → `createSessionCoordinator({ apiClient, conversationStore })`.
      The api client MUST take its token through the credential store, so the run exercises C5.
   3. Calls `apiClient.listProfiles()` and selects the profile whose `latency_class` is
      `interactive` if present, else the first profile. **Profile ids are never hardcoded**
      (requirements FR5). Prints the chosen id.
   4. Creates a conversation with that profile id.
   5. **Generation 1.** Prompt exactly:
      `My favourite number is 41. Acknowledge this in one short sentence.`
      Handlers must print, as they fire: queue position on `queued`, a "model loading" line
      on `model-loading`, and each `content` delta written to stdout with
      `process.stdout.write` so output appears progressively rather than line-buffered at
      the end.
   6. **Generation 2**, in the SAME conversation (therefore the same session). Prompt exactly:
      `What is my favourite number? Reply with only the digits.`
   7. Calls `apiClient.getSession(sessionId)` after both generations and prints the turns.
   8. Prints `apiClient.getRequestLog()` — every request the run made, in order.

B. The script then makes these assertions and **exits non-zero if any fails**, printing a
   clearly labelled PASS/FAIL line per criterion. Do not print PASS for a check you skipped.
   - **AC3**: generation 1 produced **at least 2 `content` events**; AND the elapsed
     milliseconds recorded at the first delta is strictly less than the elapsed milliseconds
     recorded at the `complete` event — measured with a monotonic clock captured inside the
     handlers, proving output was surfaced during the stream rather than after it; AND the
     `complete` telemetry was received and all four required fields are present and of the
     right type: `tokens_per_second` (number), `eval_count` (number), `quantization`
     (string), `context_limit` (number). Print those four values with labels.
     Print a line of the form:
     `AC3: deltas=<n> firstDeltaMs=<x> completeMs=<y> tps=<..> eval_count=<..> quantization=<..> context_limit=<..>`
   - **AC4**: generation 2's accumulated assistant text contains `41`. Print the full text of
     answer 2 so a human can see the context was carried, along with the session id shared by
     both generations.
   - **AC5**: the `getSession` snapshot has **exactly 4 turns** with roles in the order
     user, assistant, user, assistant; turn 0's content equals prompt 1 and turn 2's content
     equals prompt 2. Therefore exactly one user turn and one assistant turn per generation,
     and no duplication. Print the count and the role sequence.
   - **(derived: FR4)**: `getRequestLog()` contains **zero** entries whose URL contains
     `/turns`. Print the total request count and the count of `/turns` requests (which must
     be 0). Also print the full log so the absence is visible rather than merely asserted.
   - Print a final `M2 LIVE PROOF: PASS` only when all four passed.
