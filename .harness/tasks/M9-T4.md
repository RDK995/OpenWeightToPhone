Goal:
Add the thin mounting layer that turns the already-built pure view-model and action map
into a running client, and prove that the bundle the asset server serves actually builds
and mounts. Four new source files, one rewritten entry point, two new test files.

Background — the design boundary you must respect:
There is no browser under any agent's control here (no Node, no Playwright, no device).
So this milestone deliberately splits the client in two:
  - Everything testable WITHOUT a DOM: `view-model.ts` (done), `actions.ts` (done), and

2. **`web/src/ui/mount.ts`** (new) — DOM-free. Exports exactly these, verbatim:
   ```ts
   import type { SessionCoordinator } from "../session-coordinator";
   import type { ConversationStore } from "../conversation-store";
   import type { Profile } from "../api-client";
   import type { RenderTarget } from "./render-target";
   import type { UiActions } from "./actions";
   import type { UiState, GenerationDisplay } from "./view-model";

   export interface MountDeps {
     target: RenderTarget;
     coordinator: SessionCoordinator;
     store: ConversationStore;
     initialState?: {
       selectedConversationId?: string | null;
       profiles?: readonly Profile[];
       generation?: GenerationDisplay;
       streamingText?: string;
     };
   }

   export interface MountHandle {
     getState(): UiState;
     render(): void;
     select(conversationId: string | null): void;
     setGeneration(generation: GenerationDisplay): void;
     setStreamingText(text: string): void;
     setProfiles(profiles: readonly Profile[]): void;
     actions: UiActions;
   }

   export function mount(deps: MountDeps): MountHandle;
   ```
   Behaviour, all of which must be tested:
   - On call, it builds a `UiState` from `deps.store.loadConversations()` plus the
     `initialState` overrides, defaulting `selectedConversationId` to `null`, `profiles` to
     `[]`, `generation` to `{ kind: "idle" }` and `streamingText` to `""`.
   - It paints EXACTLY ONCE during `mount(...)`, via
     `deps.target.paint(buildViewModel(state))`.
   - `render()` re-reads `deps.store.loadConversations()` (so newly created or deleted
     conversations appear), rebuilds the state, and paints again. Test that a conversation
     added to the store between two `render()` calls shows up in the second paint — that is
     what proves it re-reads rather than caching.
   - `select`, `setGeneration`, `setStreamingText`, `setProfiles` each update the held state
     and then paint. Test each one causes exactly one additional paint carrying the new
     value.
   - `getState()` returns the current state. It must NOT hand out a reference that lets a
     caller mutate the mount's internal state — return a copy. Test that mutating the
     returned object does not affect the next paint.
   - `actions` is `createActions(deps.coordinator)` — reuse the existing module, do not
     reimplement any delegation.
   - **`mount.ts` must contain no `document`, no `window`, no `localStorage`, no `fetch(`,
     and no runtime (non-`import type`) import of `./dom-target`.** Add a structural test
     asserting this over the file's text, modelled on the existing bypass test in
     `test/web/ui/actions.test.ts` — read that test and reuse its approach and its
     `import type` allowance.

3. **`web/src/ui/dom-target.ts`** (new) — the ONLY module in `web/src/` permitted to touch
   the DOM. Exports:
   ```ts
   export function createDomTarget(root: HTMLElement): RenderTarget;
   ```
   Keep it minimal and obvious: on `paint(view)`, render the conversation list, the
   transcript, the profile list and the generation status into `root`. Plain DOM calls
   (`createElement`, `textContent`, `replaceChildren`), no framework, no innerHTML with
   interpolated content, no styling beyond what already exists in `index.html`. Render the
   generation status so each of the seven `GenerationDisplay` kinds is distinguishable to a
   human reading the screen, including the 1-based queue position and, on `complete`, the
   four telemetry values (tokens per second, eval count, quantization, context limit).
   This module is NOT unit-tested here — it is attested on the device in M10. That is the
   reason to keep it short.

4. **`web/src/main.ts`** (rewrite) — the bundle entry point. It must:
   - Re-export the client surface so the built bundle exposes it:
     `mount`, `createDomTarget`, `createActions`, `buildViewModel`, `toTelemetryDisplay`.
   - Export `bootstrap(root: HTMLElement): void`, which wires the real collaborators and
     mounts: the `localStorage`-backed storage port, the conversation store, the credential
     store, the api client, the session coordinator, and `createDomTarget(root)`. Read the
     exported factory functions in `web/src/storage-port.ts`, `web/src/credential-store.ts`,
     `web/src/api-client.ts` and `web/src/session-coordinator.ts` and use their real
     signatures — do not invent them.
     **If no credential is stored, `bootstrap` must still mount and paint (an empty
     conversation list) rather than throwing.** Pairing is milestone M11's job; a client
     that throws before pairing would make M10's on-device check impossible.
   - Run the browser bootstrap ONLY behind a guard: `if (typeof document !== "undefined")`.
     Inside that guard, resolve the root element (`document.getElementById("app")`) and, if
     present, call `bootstrap(root)`. Preserve the existing app-shell readiness marker
     `document.documentElement.dataset.appShell = "ready"` — M1 established it and nothing
     may regress it.

     makes criterion 5 possible, and it is the single most likely thing to get wrong: any
     top-level statement that touches `document`, `window` or `localStorage` OUTSIDE the
     guard breaks it — including inside a factory you call at module scope.
