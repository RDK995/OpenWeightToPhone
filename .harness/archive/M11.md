## M11 — Scanning the QR code pairs the phone with the harness

Status: DONE

### Outcome

The Mac-side pairing CLI renders a QR code encoding
`https://ryans-mac-studio.tailc3648a.ts.net/app/#t=<token>`. The token sits in the URL
fragment specifically because fragments are never transmitted to a server, so scanning
cannot leak the credential into the harness's logs or Tailscale's. The PWA captures the
token from `location.hash`, persists it, and clears the hash immediately.

The token is read from `~/.openweight-harness/token` (honouring
`OPENWEIGHT_HARNESS_TOKEN_FILE`), and reading is refused outright if the file is group- or
world-readable — a disclosed credential should stop the tool, not be used anyway. The live
file is currently mode `0600`, so the refusal path is proven against a fixture file created
with looser permissions, not by changing the real one.

**AC2 is split by what is provable.** The camera scan itself is human-attested: only the
human can point an iPhone at the terminal. Everything either side of the camera is proven
mechanically — the QR round-trip (AC1), and the credential store's behaviour given the
pairing URL's fragment: it extracts the token, persists it through C11, clears the
fragment, and a subsequent call to the live harness with the stored token returns `200`.
A reviewer is therefore asked to sign off an attestation covering only the optical step.

Pairing comes last because it needs the app already served at `/app` (M1) and installable
(M10) for a scan to land somewhere useful.

### Attestation — AC2, 2026-09-01, human on iPhone (phone-only, no Studio access)

**AC2 is FALSIFIED on device. M11 is not complete.**

The human was away from the Mac Studio, so the QR could not be rendered to a terminal for a
live camera scan. With the credential-exposure trade explicitly accepted, the pairing QR was
rendered to a PNG and delivered to the phone for the Photos-based decode path. Before that,
the PNG was round-tripped through `scripts/qr-decode.swift` (Apple Vision) and the decoded
payload's SHA-256 matched the expected pairing URL's byte-for-byte, so the QR itself is
sound. `GET /app/` returned `200` over the tailnet.

**What the human observed:** opening `https://ryans-mac-studio.tailc3648a.ts.net/app/` with
no stored token, and opening the same app via the QR's `#t=<token>` fragment, produced
**an identical Idle page**. The scan did not pair the phone.

**Root cause, confirmed mechanically and not by inspection alone:**
`adoptCredentialFromFragment` (`web/src/credential-store.ts:85`) is never called from
`bootstrap()` in `web/src/main.ts`. Its only callers are `test/web/credential-store.test.ts`
and `src/host/m11-proof.ts`. Because nothing in the app calls it, the bundler tree-shook it
out entirely: `web/dist/main.js` contains **zero** occurrences of
`adoptCredentialFromFragment` and **zero** occurrences of `location.hash`. The shipped app
has no fragment-capture code in it at all.

**Why 711 passing tests did not catch this.** Every proof of AC2 injected its own
`LocationPort` and `StoragePort` and called the adopter directly, so all of them proved the
unit in isolation. None asserted that the browser entry point wires it up, and none asserted
against the built bundle. This is a proof-design defect, not only a wiring omission: a
correction that adds the call without also adding a proof that would fail if the call were
removed leaves the same hole open.

**Scope of the attestation.** This exercised iOS's *decode* path (Photos/Vision), not the
camera optics. The optical step therefore remains outstanding even once the wiring is fixed,
and must be attested at the Studio before AC2 can be ticked. The Private-Browsing context
also clears storage on tab close, so "stays paired across launches" was not under test.

**Credential note.** The QR encoding the live bearer token was transmitted through the
assistant conversation to reach the phone. The human accepted this trade knowingly. The
token should be regenerated; `~/.openweight-harness/token` was not modified by the harness.

### AC2 Correction — 2026-09-01 (implementation phase 3)

The falsification above was acted on. **The defect was not re-litigated; it was fixed**, and
the proof design that let it ship was fixed with it.

**What was wrong.** `bootstrap()` in `web/src/main.ts` never called
`adoptCredentialFromFragment`, so the bundler tree-shook the function out and the shipped
`web/dist/main.js` contained no fragment-capture code at all. A second, latent defect sat in
the same function: `createApiClient` captured `credential?.baseUrl ?? ""` from a credential
read *before* any adoption could occur, so adopting late would still have left the client with
an empty base URL — the app would have stored the token and then failed to use it.

**What changed.**

- **`web/src/location-port.ts` (new)** — `createWindowLocation(win: Window): LocationPort`.
  `hash` and `origin` are **live getters** delegating to `win.location`, not values snapshotted
  at construction (a snapshot would read stale after `clearHash()`). `clearHash()` uses
  `win.history.replaceState(null, "", pathname + search)` — **`replaceState`, so no history
  entry**; never assignment to `location.hash`/`href` (which adds an entry, leaves a bare
  trailing `#`, and can fire `hashchange`); **no reload**. It falls back to
  `win.location.replace(...)` when `history.replaceState` is unavailable and **never throws** —
  a throw here would abort bootstrap and leave the token sitting in the URL, which is strictly
  worse than a fragment that lingers. The module takes `win` as a parameter and touches no
  global, so importing it outside a browser cannot throw.
- **`web/src/main.ts` (modified)** — `bootstrap(root, deps?)` now adopts **before** it reads
  the credential for the API client. `BootstrapDeps` makes `storage`, `location`,
  `createTarget` and `createApiClient` injectable, each defaulting **lazily** to exactly the
  production collaborator used before (`createLocalStorageStorage(window.localStorage)`,
  `createWindowLocation(window)`, `createDomTarget`, `createApiClient`). Lazily matters: a test
  process has no `window`, so an eager `??` fallback would throw. The browser path
  (`bootstrap(root)` under `typeof document !== "undefined"`) is unchanged.

**The proof-design fix — the half that matters as much as the wiring.** Every pre-existing
AC2 proof injected its own ports and called the adopter directly, so all of them would have
passed against an app that never calls it. That is why 711 tests missed a completely broken
pairing flow. Three new layers were added, each of which **fails if the call is removed from
`bootstrap()`**:

1. **`test/web/main-bootstrap.test.ts` (new, 9 tests)** — calls `bootstrap()` itself with
   injected ports and asserts the credential is adopted, the hash is cleared, and — the
   ordering proof — that the API client is constructed with the **adopted** base URL rather
   than `""`. Negative controls cover no-fragment, already-stored-credential and
   `#a=1&t=tok` cases.
2. **`test/web/bundle-fragment.test.ts` (new, 4 tests)** — builds the bundle, then asserts
   against **`web/dist/main.js`, the artefact actually served**: statically that it wires the
   adopter into `bootstrap`, and behaviourally by cache-busted dynamic import of the built
   file, calling **the bundle's own `bootstrap`** and observing adoption, hash clearing and the
   adopted base URL. A no-fragment negative control proves the assertion discriminates.
3. **`src/host/m11-proof.ts` Phase 2 (rewritten)** — no longer rests on calling the adopter
   with a fake location. It builds the bundle, checks the bundle wires the adopter, imports the
   **built** bundle, runs its `bootstrap()` against the real pairing URL's fragment, then reads
   the token back **only out of the storage the bundle wrote** (never from `readToken()` again
   at that point) and uses it as the bearer for a live `GET /v1/profiles` → **200**, with the
   unauthenticated **401** control retained. The shipped artefact is thereby chained to a live
   authenticated call.

**The static assertion was caught being vacuous, and fixed (T9-fix).** T9's first attempt
asserted `toContain("adoptCredentialFromFragment")` against the bundle. Because `main.ts`
*exports* that symbol, the identifier survives tree-shaking whether or not anything calls it:
with the wiring removed the bundle still held **2** occurrences and the assertion still passed
(RED run: 3 pass / 1 fail — only the behavioural assertion fired). A worker reported this as
PASS; **the claim was overturned on its own evidence.** Both the test and the proof script now
assert the **call site** (`adoptCredentialFromFragment(credentialStore`), which the function's
*definition* (`function adoptCredentialFromFragment(store, location)`) and the bare export list
cannot satisfy. Catching a non-discriminating proof inside the fix for a non-discriminating
proof is the reason this is written down rather than quietly corrected.

  `test/qr/encode.test.ts`. **19 pass / 0 fail, 228 expect() calls.** Two Cheap attempts
  failed honestly (each left the failing round-trip test in place rather than weakening it);
  the Mid-tier attempt found and fixed **seven distinct bugs**, and the sequence is worth
  recording because the earlier attempts were guessing at whole-grid diffs while the fix

    2. `createDataCodewords` computed `totalBytes` from the bit-packing maths alone, so the
       `0xEC`/`0x11` filler loop **never ran**; it now pads to `totalDataCodewords(version, ecc)`.

- **Proof-design lesson, worth generalising beyond M11.** Two defects this milestone —
  the shipped bundle losing the fragment-capture code, and T9's vacuous static assertion —
  were both *non-discriminating proofs*: assertions that pass whether or not the thing they
  describe is true. The suite was 711 green while the app was completely broken. Whenever a
  criterion is proven by injecting ports into a unit, **something must also assert the real
  entry point and the built artefact**, and the red state must be demonstrated rather than
  assumed. Worth applying to M2-M10's criteria as a sweep.
- **`test/build.test.ts` deletes `web/dist` in its `afterEach`,** so a full `bun test` run
  leaves the served bundle **absent**. Anything that serves `/app/` after a test run must
  rebuild first. This is a live foot-gun for the deployed PWA, not just a test-ordering
  nuisance: `bun run scripts/build.ts` must be the last command before serving. Consider
  building into a temp dir in that test instead.
- **`bunx tsc --noEmit` resolves `typescript` from the network** rather than from
  `devDependencies` (a worker hit `Script not found "tsc"` once, and successful runs print
  "Resolving dependencies / Resolved, downloaded and extracted"). The type check is therefore
  network-dependent and not reproducible offline. Add `typescript` to `devDependencies`.
- **`bun` is not on `PATH` for non-login shells** (`/Users/ryankenny/.bun/bin/bun` is the
  absolute path). Scripted validation should not assume a bare `bun`.
- **AC2's optical step still needs a human attestation.** Everything either side of the
  camera is proven mechanically, but only the human can point an iPhone at the terminal and
  confirm that scanning the rendered QR lands a working authenticated client with
  `location.hash` cleared. AC2's box is deliberately left unchecked until that attestation
  exists — the same pattern M10 used for its on-device install.
- **`test/host/pair.test.ts` hard-codes an absolute project root**
  (`const projectRoot = "/Users/ryankenny/Projects/phoneToLocalModel"`) to locate
  `scripts/qr-decode.swift`. It works here and nowhere else. Derive it from `import.meta.dir`
  when the file is next touched. `test/qr/encode.test.ts` should be checked for the same
  pattern.
- **The N4 mask penalty uses a simplified formula.** `evaluateMasks` in `src/qr/encode.ts`
  computes the dark/light balance penalty as `floor(deviation/5)*10` rather than the canonical
  min-of-floor/ceil variant. This only affects which of several valid masks is chosen — every
  mask is proven decodable by the Reed-Solomon self-consistency oracle and by full Vision
  round-trips — so it costs a little redundancy margin, not correctness.
- **The QR encoder is capped at versions 1-10**, which comfortably covers the 93-byte pairing
  URL at every ECC level (it currently lands at v6/M). If a longer payload is ever encoded,
  versions 11-40 need their capacity, block-structure and alignment tables added.
- **T2's round-trip assertion is guarded rather than asserted-through.** In
  `test/host/config.test.ts` the decode check sits inside
  `if (fragmentMatch && fragmentMatch[1] !== undefined)`. It is **not** vacuous today —
  `expect(fragmentMatch).not.toBeNull()` runs immediately before it, and a sibling test
  asserts `toContain(encodeURIComponent(specialToken))` unconditionally — but the pattern
  would silently stop asserting if the regex were ever changed. Worth converting to a
  non-optional narrowing when the file is next touched. This is the same failure mode as
  T6-fix, and the two are worth fixing together.
- **`gfExp` extension comment in `src/qr/reed-solomon.ts` is inaccurate.** It claims indices
  510-511 read uninitialised entries and are "unreachable in practice"; in fact
  `gfExp[i-255]` for `i = 510,511` reads `gfExp[255],gfExp[256]`, both written earlier in the
  same loop. The `?? 0` guard is harmless and the syndrome oracle proves the maths, but the
  comment should be corrected.
