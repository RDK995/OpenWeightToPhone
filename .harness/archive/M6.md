## M6 — A conversation survives losing its server session

Status: DONE

### Outcome

A prompt sent against a session the service no longer holds returns `404 unknown_session`.
The client creates a fresh session, replays the locally stored transcript via
`POST /v1/sessions/{id}/turns`, and continues the conversation with its context restored.

**How the `404` is induced.** Restarting the harness process is an explicit non-goal
("Managing models or the harness process itself"), so the agent must not restart it. The
API contract defines `unknown_session` as "Session id does not exist **or was lost on
service restart**" — the two are indistinguishable to a client, and the recovery path is
identical. The live proof therefore drives a stored conversation at a session id the
service does not hold. If the operator wants confirmation across a genuine restart, that is
a human-attested extra and is recorded as such; it is not this milestone's mechanical proof.

### Follow-ups

- **The "prompts re-pairing" clause of M6's second acceptance criterion is not covered by
  this milestone.** `send()` correctly distinguishes `401` from `404` and refuses to
  rebuild or replay on a `401`, which is what M6 can prove today, but the `401` simply
  propagates to the caller and nothing turns it into a re-pairing prompt. Whichever
  milestone owns the client's error surfacing (M7) or the pairing flow (M11) must close
  this, and should treat it as a named carry-over rather than discovering it fresh.
- `appendTurn` throws `new HarnessApiError("invalid_response", 201, data)` with the
  status hardcoded rather than `response.status`. Harmless — `handleResponse` only
  returns for `response.ok`, and 201 is the documented success status — and it matches
  the existing convention in `createSession`, `getSession` and `cancel`, which all
  hardcode `200`. Worth tidying across all four at once, not in isolation.
- `resumeIfInterrupted` does **not** recover from `unknown_session`; only `send()`
  does. A backgrounded page returning after the service lost the session will see the
  `404` propagate out of `resumeIfInterrupted` unhandled. M6's acceptance criteria
  cover `send()` only, so this was deliberately left out of scope. It is a real gap in
  FR8 coverage and should be picked up by whichever milestone owns the resume path's
  error surfacing (M7 is the natural home).
- The two verifier misattributions above both stemmed from the verifier constructing
  its own baseline commit because this repository keeps nearly all source untracked
  (2 commits total). Every future milestone's review will hit the same problem. Worth
  committing the working tree so diffs are computable, as a project-level chore.
