## M2 — A prompt to the live harness streams incrementally and reports telemetry

Status: DONE

### Outcome

The walking skeleton of the client stack. A Mac-run entry point, built from the same
TypeScript modules the browser will load, creates a session against the live harness,
sends a prompt, prints assistant output incrementally as `content` events arrive, and
prints the `complete` event's telemetry. It then sends a second prompt in the same
conversation and shows the model had context from the first.

The entry point is a CLI because there is no browser under this agent's control; the
modules exercised (C5, C6, C7, C8, C9, C11) are the same ones the PWA mounts, with C11
memory-backed under test and `localStorage`-backed in the browser. **AC3 is owned here and
proven at this entry point** — incremental rendering means output written as deltas
arrive, not buffered. M9 re-exercises the same coordinator through the browser view and
does not re-own AC3.

Everything is proven against the live service.

build predating the session routes, so `POST /v1/sessions` and every generation endpoint
returned `404 not_found`. The cause was a stale, unsupervised process (PID 32470, started

routes. The fix required killing an operator-started process, which the sandbox denied, so

  The incrementality criterion is proven *empirically*, not asserted: the verifier replaced the
  implementation with a buffering one and the test **timed out at 5000 ms**, then passed in 7 ms

  `onDelta` must fire while the stream is still open — a buffering coordinator cannot pass it.

### Known issues

- **The repository as a whole does not typecheck, and never did.** `bunx tsc --noEmit` reports
  errors across M1's files too (`src/host/config.ts` 10, `src/host/pwa-server.ts` 9,
  `src/host/serve-install.ts` 9, `scripts/build.ts` 7) as well as most test files. The root
  cause is that `@types/bun` is not installed, so `bun:test`, `Bun` and `process` do not
  resolve, cascading into unrelated-looking errors. TypeScript is not even a project
  dependency — `bunx tsc` downloads it on demand — and there is no `typecheck` script, so this
  has never been a gate. M2 left `web/src` clean but deliberately did not fix the wider
  problem: it spans M1's code and requires adding a dependency, which is outside this
  milestone's scope. **Recommended follow-up:** add `@types/bun` and a `"typecheck"` script,
  wire it into the test gate, and clear the residue. Until then, green tests do not imply
  type-correct code — which is precisely how T4b's 8 real errors survived unnoticed.
- The conversation store's `updatedAt`-descending ordering test forces distinct millisecond
  timestamps with 5 ms busy-waits. It passed five consecutive runs under verification, but it
  is time-dependent by construction; injecting a clock would be sturdier if it ever flakes.
- The harness API server remains unsupervised (carried over from the resolved blocker above). A
  stale process would re-block M3-M9 in exactly the same way.

- **OPTIONAL (review cycle 1): `src/host/m2-proof.ts` prints a 20-character prefix of the
  live bearer token** to stdout at `src/host/m2-proof.ts:26` — roughly half of the
  ~44-character credential, which can survive in scrollback or a screen recording. Not a
  product defect (this is a developer-only proof harness), but it cuts against FR1's own
  care that the CLI "does not print the token in plain text by default". Suggested: print a
  presence/length indicator, or the last 4 characters only.
- **OPTIONAL (review cycle 1): the Known issues tally understates M2's own contribution to
  the whole-repo typecheck backlog.** `src/host/m2-proof.ts` adds 11 `tsc --noEmit` errors of
  the same class (missing `@types/bun`/`process`, plus `TS5097` for `.ts`-suffixed imports) —
  more than any single M1 file cited there. Same root cause, and `web/src` is genuinely
  clean, so this is a bookkeeping correction for whoever clears the backlog, not a defect.
