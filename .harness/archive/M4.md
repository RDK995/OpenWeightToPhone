  a genuine mid-generation cancel. So it is unknown whether the service records an empty
  assistant turn, a turn with empty content, or no turn at all in that situation. If it
  records none, the local mirror would hold a turn the service does not — a divergence the
  third criterion does not catch. Worth probing and reconciling; not a defect against any M4
  criterion as written.
- **`.harness/milestones.md` is over the ~400-line archiving threshold (1111 lines) and
  nothing is archivable yet.** M1 and M2 are already archived to `.harness/archive/`.
  The only other settled milestone is M3, and it is the *most recently settled*, which the
  archiving rule holds back precisely so the next session can see it. M5-M11 are `TODO` and
  M4 is active, so neither qualifies. Archiving was considered this cycle and correctly
  declined, not overlooked. The moment M4 reaches `DONE`, M3 becomes archivable and M4
  takes its place as most-recent — archive M3 then. Most of the current bulk is M4's own
  entry plus the seven unstarted milestones, neither of which archiving addresses.
- **The already-`failed` idempotency case is not provable from the client.** The
  requirement (`.harness/requirements.md` lines 145-146) names three terminal states for
  idempotent cancel — already-complete, already-**failed**, already-cancelled. M4 proves
  `complete` and `cancelled` live. It does **not** prove `failed`, and cycle 1 established
  by live probe that it cannot: every malformed request is rejected at the HTTP layer
  before a generation id exists (`unknown_profile` -> 400, `invalid_request` -> 400,
  `unknown_session` -> 404; no `x-generation-id` header, no id in any body), so there is
  nothing to cancel. The only remaining routes to a `failed` generation are
  `inference_failed`, which has no client-side lever, and `generation_timed_out`, which
  needs a 300s wait. The `failed` case therefore rests on the documented API contract plus
  the fact that `cancel()` forwards the service's `status` string verbatim with no
  per-value branching — i.e. on **inference, not live proof**, which is exactly the
  distinction this project's standing rule exists to keep visible. Closing it needs a
  server-side lever to force an `inference_failed` generation (a fault-injection profile,
  or a test hook); that is not M4's to build. Same class as the empty-partial-output gap
  below.
- **The `error` terminal path still records no assistant turn**, so partial output from a
  failed generation is dropped locally even though the service may have recorded it. Out of
  scope for M4 (the criteria are about cancellation), and likely M7's business when error
  surfacing is built.
- **`cancel(conversationId)` depends on `pending` being set**, which `send` writes only after
  the generation is admitted. A cancel issued between the user pressing send and admission
  completing will throw `No generation in flight`. Acceptable for M4, but the UI (M9) will
  need to handle it rather than surfacing the raw error.
- **C9 `cancel()` is unusable once a generation reaches a terminal state**, because `send`
  clears `pending` on every terminal path. The idempotency behaviour the second criterion
  proves is therefore reachable through C7 but not through C9. M4 does not require it (the
  criterion is about the service's response), but if the UI ever needs to re-query or
  re-cancel a finished generation through the coordinator, C9 will need a way to address a
  generation by id rather than only the in-flight one.
