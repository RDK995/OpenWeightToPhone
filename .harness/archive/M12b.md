## M12b — Changing a conversation's profile actually changes it

Status: DONE

### Outcome

**Found by the human on the device, on 2026-09-01, after M12's cycle-2 review had already
returned PASS.** The profile selector is inert from the user's point of view: picking a
different profile leaves the app showing the old one, so the human reported being "stuck on
Fast reasoning".

This milestone exists because the human chose to **defer** the fix rather than override M12's
spent review/fix cap. It is not new scope: FR5 requires that "Profile is selectable per
conversation and changeable", and M12's criterion 1 already covers the profile selector. M12 is
therefore settled on its own recorded criteria and this repairs a requirement it left unmet. It
**runs before M13**.

**The defect is the same one M12's fix cycle already repaired twice, in the one place it did not
apply the correction.** `web/src/ui/dom-target.ts`'s profile `change` handler calls

```ts
deps.actions.chooseProfile(selectedConversationId, selectedProfileId);
```

with no `await`, no `render()`, and no `.catch()` — exactly the shape that BLOCKER 1 fixed for
`create-conversation` and `delete-conversation`. Verified downstream while diagnosing:
`session-coordinator.ts`'s `setProfile` (line 602) delegates to `conversation-store.ts`'s
`setProfileId`, which does mutate `profileId`, stamp `updatedAt` and `persist()`; and
`dom-target.ts`'s `paint` rebuilds the `<option>` list marking `view.selectedProfileId`
(`view-model.ts:123`, `selectedConversation?.profileId`). So the write lands, but nothing
repaints at the moment of change and any rejection is unhandled.

**Why two agent reviews passed over it.** The tests assert that the `change` event *dispatches*
`chooseProfile` with the right arguments — not that the selection is *reflected* afterwards.
This is the same lesson M12 recorded in blood and did not finish applying: **evidence that an
action was invoked is not evidence that it took effect.** Any test written here must fail if the
repaint is removed.

### Follow-ups

- **DONE this milestone:** the cancel handler's missing `.catch()` (described in the
  note below) was fixed as part of the derived-FR9 criterion, and is covered by
  Test D. The note is retained below for the reasoning it records. The missing
  `render()` on cancel was deliberately **not** added, per that same note.

- **`deleteConversation` needs no `.catch()`** — checked while here, to close out
  the defect-class sweep the note below asks for. `UiActions.deleteConversation`
  is declared `: void`, not `Promise<void>`, and `createActions` implements it
  synchronously over `store.deleteConversation`. There is no promise to reject, so
  the "fire a promise, never catch" class does not apply. The sweep is now
  complete: `create`, `delete`, `profile`, `cancel` all accounted for.

- **The live proof's profile B is the harness's first-listed profile**
  (`reasoning-baseline`, the only `interactive` one). It was chosen because a
  `batch` profile timed out the generation in attempt 1. The risk is that a
  harness defaulting to its first profile would produce the same telemetry
  whatever the app sent — so telemetry alone would be weak evidence here. It is
  not weak in fact, because the proof also asserts the generate **request body**
  carried B's id and that both oracles differ from profile A's id. Still, a
  non-default profile B would make the proof self-evidently strong rather than
  strong-on-inspection. Worth revisiting if a second `interactive` profile ever
  exists.

- **The pre-existing dispatch-only test remains** at
  `test/web/ui/dom-target.test.ts` ~line 360 ("profile-select change dispatches
  actions.chooseProfile"). It was deliberately left in place and unweakened — it
  still guards the dispatch — but it is the weaker style this milestone was
  created to supplement, not the evidence any criterion rests on.

- **Archiving:** `.harness/milestones.md` went 2540 → 1352 lines this phase (M12
  and M12a-i moved to `.harness/archive/`). It is still above the ~400-line
  threshold. `## M12a-ii` (612 lines) is the largest remaining block and became
  archivable only once M12b settled — archive it next phase, once M12b is no
  longer the most recently settled milestone.

- **Check the other `UiActions` call sites for the same shape while you are here.** The defect
  class is "fire a promise, never repaint, never catch". `create`, `delete` and now `profile`
  have been found. **`cancel` was checked while writing this entry, and the answer is: partly.**
  `dom-target.ts`'s cancel handler calls `deps.actions.cancel(selectedConversationId)` with no
  `await`, no `render()` and no `.catch()` — the same shape. But unlike profile, its *visible*
  effect does not depend on that call repainting: the in-flight generation's own event stream
  fires `onCancelled`, which calls `controller.setGeneration({ kind: "cancelled" })`, and that
  repaints through `mount.ts`. So cancel is expected to work on screen, and the missing repaint
  is not a user-visible defect there.
  **The missing `.catch()` still is one**, though a lesser one: if the cancel request itself
  fails — an offline tailnet, a `401` — the rejection is unhandled and the user is told nothing,
  which is the FR9 gap M12 closed for send and profile-fetch but not here. Fix it alongside the
  profile handler; it is one line in the same file and the same defect class.
