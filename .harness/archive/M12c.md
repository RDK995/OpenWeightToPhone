### Outcome

**Requested by the human on 2026-09-02**, after M12 and M12a-ii were attested on the device and
the app was confirmed working end to end. The client is functionally complete for FR3 and FR4 but
presents them as nested bullet lists with the conversation list, controls and transcript stacked
in one column — a debug rendering of a working client rather than something to hold.

**This needs no requirements change, and that is the reason it is a milestone rather than a
`roast-requirements` cycle.** FR3 already requires "A list of conversations, newest first,
supporting create, open, and delete", and FR4 the incrementally streamed transcript. Both are
built, reviewed and attested. This milestone changes how they are *presented*; it adds no
capability and removes none.

**The warm/cold "what is loaded" indicator the human asked for in the same breath is deliberately
NOT here.** Nothing in FR1-FR9 asks for it, and it makes a claim about the Mac's state that the
API cannot substantiate — `/v1/profiles` exposes five fields and never a model name, `/status` is
a frozen three-field M0 contract, and there is no models endpoint. It goes through
`harness:roast-requirements` separately so it gets an honest acceptance criterion. The full
finding and the settled fallback (drop the indicator, keep the dropdown — do **not** add a harness
endpoint) are recorded in `.harness/ui-redesign-brief.md`.

**SETTLED with the human on 2026-09-02 — the conversation list is a slide-over drawer, not a
permanent left column.** At 390pt a fixed column leaves roughly 250pt for messages. The chat fills
the screen; the list slides in from the left over it. Do not re-litigate this into a split view.

**It runs after `M12b`**, because the drawer's profile control sits on top of a selector that does
not currently repaint when changed, and stacking a redesign on a known-broken control makes both
harder to review.

**Sequencing hazard with `M13`, recorded so it is a decision rather than an accident.** M13's
long-transcript criteria measure that streaming deltas do not create DOM elements proportional to
transcript length — in this same renderer. A chat-bubble rewrite lands directly on that code. This
milestone therefore carries its own narrow incremental-growth guard (criterion 4) so the redesign
cannot regress what M13 will later measure, but the two should not be run concurrently.

### Architecture

C10. No new component and no new boundary expected: this is presentation inside the component
already agreed to "Render the conversation list and chat view". `web/src/ui/dom-target.ts` is one
of only two modules permitted to touch the DOM, and the DOM-free `view-model.ts` / `actions.ts` /
`mount.ts` split is structurally enforced by tests — stay inside it rather than routing around it.
Confirm rather than assume whether a `## Deviations` entry is owed; adding a drawer with its own
open/closed state may push presentation state into the view-model, which is worth recording.

**Styling is hand-written CSS.** The architecture's settled mitigation for holding the bearer
token in `localStorage` is that the bundle ships no third-party code, and
`test/web/bundle-purity.test.ts` enforces it. No framework, no icon library, no web fonts.

### Acceptance Criteria
- [ ] (FR3) The conversation list renders in a drawer that is closed by default, with a control
      that opens it and a tap-outside or dismiss gesture that closes it. Opening and closing the
      drawer does not unmount or rebuild the chat transcript. The assertion must fail if the
      drawer is removed or left permanently open.
- [ ] (FR3) Selecting a conversation from the drawer opens it in the chat view **and** closes the
      drawer in one action, with no second tap required. Create and delete remain reachable from
      the drawer and still invoke exactly their existing `UiActions` calls — no control reaches
      C7, C8 or C9 except through the actions map.
- [ ] (FR4) The transcript renders as chat bubbles: user and assistant turns are visually
      distinguished from each other, one bubble per turn, in the view-model's own order. A turn
      recorded `cancelled: true` is still marked as cancelled rather than presented as a complete
      answer, and the `complete` telemetry line is still rendered.
- [ ] (FR4, guard) Streaming grows the active assistant bubble in place rather than appending a
      node per delta: applying a run of `content` deltas creates a number of elements that does
      not scale with the number of deltas. The assertion must fail if the renderer reverts to
      rebuilding. This exists so the redesign cannot regress what `M13` will measure.
- [ ] (derived: FR2, iOS) No interactive control renders under the iOS status bar or the home
      indicator in the new layout — the safe-area inset fix M12 shipped in
      `web/public/index.html` must not regress, and the drawer must respect it too.
- [ ] **Human-attested on the physical iPhone (`iphone-15-pro`).** In the installed home-screen
      app the drawer opens, a conversation can be picked from it, and the chat reads as a phone
      chat app. **Not agent-provable** — no agent may check this box.

### Follow-ups

- **Do not let the redesign quietly widen into the indicator.** The dropdown may show which
  profile is selected for the conversation — that is FR5 and already exists. It must **not** claim
  anything about what is loaded on the Mac until that requirement is agreed.
- **`happy-dom` is the existing DOM test vehicle** and is test-only. Layout assertions should
  prefer structure and applied classes over pixel geometry, which `happy-dom` does not compute.
  A criterion that silently degrades to asserting nothing is the failure mode this project has
  already recorded twice.
