asset server alive, so the app is there whenever the phone is picked up.

**AC10 is human-attested.** Installing to the iOS home screen and observing standalone

### Open Problem — derived criterion 3: ROOT CAUSE FOUND, NOT FIXABLE INSIDE C13

**The cause is a host-level fault in the `gui/501` launchd domain, not a defect in our
plist.** The domain is holding a non-zero on-demand refcount, which puts it in
"on-demand-only mode", in which launchd pends *every* non-demand spawn indefinitely.
`KeepAlive` and `StartInterval` respawns are both classified non-demand, so both are pended.

Three attempts, all honest failures, none weakening the proof:

1. **T5 (Mid, attempt 3)** reproduced the failure across five full runs plus one isolated
   6+ minute observation, and hypothesised `ProcessType: Background`.
2. **T6 (Mid, attempt 3 of the fix)** tried `Standard`, omitting `ProcessType`, `Interactive`,
   and `ThrottleInterval: 1`. **All four behaved identically**, falsifying T5's hypothesis.
3. **T7 (Top, attempt 4)** ran the diagnostic investigation neither Mid attempt had, and
   **changed no files** — correctly returning BLOCKED rather than manufacturing a pass or
   building the forbidden material change.

**T7's evidence, independently re-verified by the orchestrator on the live machine:**

- `launchctl print gui/501` header reports **`on-demand count = 1`** (`type = login`,
  `session = Aqua`, `creator = loginwindow[400]`). Verified directly.
- `/sbin/launchd` contains the format strings **`pending spawn, domain in on-demand-only
  mode: %s`**, `entering ondemand mode`, and `underflow of on-demand count` — so the
  mechanism and the refcount-imbalance hazard are both real and named in the binary.
  Verified directly with `strings`.
- The `pended nondemand spawn = inefficient` label that misled T5 is simply launchd's
  internal *name for the `KeepAlive: true` spawn reason*, not a power/throttling signal.
  That is why `ProcessType` was always a dead end.
- **The decisive falsifying control.** `com.google.GoogleUpdater.wake` is an unrelated,
  Google-signed agent with a pure `StartInterval: 3600` and no `KeepAlive`. It is stuck in
  exactly the same state — `state = not running`, `pended nondemand spawn = interval`,
  `last exit code = 0`, **`runs = 9`** — on a host with **8 days 16:46 uptime**, where an
  hourly job should show ~200 runs. Verified directly. A job sharing none of our
  configuration failing identically proves the fault is **domain-level**, which makes any
  per-job plist key irrelevant a priori.
- T7 also built a throwaway-label lab (bare `/bin/sleep` agents, never written to
  `~/Library/LaunchAgents`) and falsified **ten** configurations, including every option
  the T7 packet permitted: bare `KeepAlive: true`; `KeepAlive` dicts `{Crashed}`,
  `{SuccessfulExit=false}`, and both; `StartInterval: 10` with and without `KeepAlive`;
  `LimitLoadToSessionType: Aqua`; `MachServices`; and all permitted keys at once. **None
  respawned.** Notably `StartInterval` — the packet's strongest candidate — is itself
  classified non-demand (`pended nondemand spawn = interval`) and so does not sidestep the
  deferral; and `{Crashed}` never even requests a spawn on SIGKILL, so it would have failed
  the criterion outright.
- Sampled at T+2s / T+12s / T+30s / T+60s / T+120s after the kill, the job's state showed
  **zero evolution**: `not running`, `active count = 0`, `runs = 2`, `pended` throughout.
  No throttle countdown, no state-machine progress.

**One claim could not be re-verified, and is recorded as unconfirmed.** T7 quoted launchd's
unified-log line `pending spawn, domain in on-demand-only mode: com.ryankenny.phone-pwa`
(44 occurrences in 12h). The orchestrator's re-query returned 0 hits — but it returned
**0 launchd events of any kind** for the same window, so the instrument read zero for
everything and the null is a retention/query artefact, not counter-evidence. The claim is
corroborated at the binary level (the format string exists) and by the domain refcount and
the Google control, all of which were verified. It is not load-bearing on its own.

**What holds the refcount was not identified.** The unified log store on this machine
retains roughly an hour, so the `entering ondemand mode` event could not be dated. An
unbalanced sleep/wake transition and the long-running `caffeinate -dimsu` (pid 28930) are
plausible suspects; there is no direct evidence for either and both are speculation.

**C1 — the substantive fix.** `web/src/sw.ts` awaited `deps.cachePut` inside the same `try`
as the network fetch, so a rejecting cache write discarded an already-successful 200: with an
empty cache the handler rethrew and the shell load failed outright, and with a warm cache it
silently served the stale build the network-first strategy exists to prevent. The correction
wraps the awaited write in its own inner `try`/`catch` inside the `if (networkResponse.ok)`
branch. **The report's suggested `void deps.cachePut(...).catch(() => {})` was deliberately
not used**: it does not catch a *synchronous* throw from `cachePut` (which would still land in
the outer catch), and making the write fire-and-forget would break the pre-existing
network-first discriminating test, which asserts the cache entry was replaced after
`handleShellRequest` resolves. The inner `try`/`catch` handles both shapes and preserves the
awaited ordering.
