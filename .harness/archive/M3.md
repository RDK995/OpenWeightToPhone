## M3 — A conversation's profile is chosen at runtime and drives the generation

Status: DONE

### Outcome

Profiles come only from `GET /v1/profiles` at runtime. A conversation carries a profile id,
that id can be changed, and the next generation demonstrably runs under it — confirmed by
`telemetry.profile_id` on the `complete` event rather than by the client's own claim.

The three live ids are `reasoning-baseline`, `reasoning-capable` and `reasoning-deep`
(verified during planning), but they are discovered, never written down. `reasoning-capable`
and `reasoning-deep` are `batch` latency class and may be slow; selectability for those may
be proven by admission (`200` plus an `x-generation-id` header) followed by a cancel,
provided at least one profile is carried through to a full `complete` with matching
telemetry.

`web/src/session-coordinator.ts` (C9) was **not** modified. It already read
`conversation.profileId` at send time and already let a `HarnessApiError` from
`apiClient.generate` propagate unwrapped, because that call sits outside its try/catch. Both
behaviours are now pinned by tests rather than left incidental.

**Why C7 gained `cancel` in this milestone.** Measured live during planning: the reverse proxy
closes an idle SSE connection after roughly 12 seconds, and `reasoning-deep`'s model load
exceeds that, so its stream closes with no terminal event. It therefore cannot be carried to
`complete` on a single connection. This milestone's Outcome anticipates exactly that and
sanctions proving such a profile "by admission (`200` plus an `x-generation-id` header)
followed by a cancel". The service also runs one generation at a time globally, so an admitted
generation that is never released jams every later step. `cancel` is the minimum needed to make
AC11 provable without jamming the service. Only the raw C7 endpoint call was added; the
coordinator-level cancel and the honest-transcript behaviour remain M4's.

### Follow-ups

- **The live proof depends on a cold model completing inside the proxy's ~12s idle window, and
  that is not guaranteed.** The T5 worker saw two runs fail at Phase 3 when both batch models
  were cold; three later runs (two by the verifier, one by the orchestrator) passed in about 7
  seconds each. The script handles the case correctly — it releases the stuck generation, logs
  it, and tries the next candidate — but Phase 3 still requires *some* second profile to
  complete, so a sufficiently cold service can fail the proof for environmental reasons rather
  than a client defect. The durable fix is client-side stream resumption via
  `GET /v1/sessions/{id}/generations/{id}/events`, which is M5's subject. Worth revisiting once
  M5 lands, so the proof can resume rather than abandon a candidate.
- Criterion 3 is currently proven by carrying **two** profiles to `complete` (A then B). The
  criterion strictly needs only the generation *after* the change to be confirmed, so this is
  stronger than required — and correspondingly more fragile to the coldness above. If it ever
  flakes, relaxing to "confirm B only" is a legitimate simplification that still satisfies the
  criterion.
- `setProfileId` bumps `updatedAt`; the sibling `setSessionId` does not. Both behaviours are now
  pinned by tests, but the inconsistency is real and someone should decide which is intended.
  Not a defect against any M3 criterion.
- No profile-listing seam exists between C9 and C10. The agreed `C10 -> C9` interface does not
  include `listProfiles`, and C10 does not depend on C7, so when the UI lands it will have no
  architected route to the selectable set. M3 did not need one — the proof calls C7 directly —
  so nothing was invented here. This should be resolved when M9 builds the chat view, and may
  warrant a recorded architecture deviation.
- **Process note for whoever runs the next phase.** Two verifiers were run in parallel, and one
  of them deliberately mutates `web/src/api-client.ts` and `web/src/session-coordinator.ts` to
  prove non-vacuity. The other observed those files being rewritten mid-run and reported a
  transient `243 pass / 1 fail`, plus stray `.bak` files it then deleted. The final tree was
  independently confirmed clean (expected file inventory exactly, no stray files, 244/0 green,
  live proof green). **Do not run verifiers that mutate shared source files concurrently.**
