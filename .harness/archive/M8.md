## M8 — Conversations are created, listed, opened and deleted, and survive a reload

Status: DONE

### Outcome

The local conversation store becomes the durable spine of the app: many conversations,
newest first, each backed by exactly one server session, each with its full transcript
persisted locally. Persistence is what makes M6's replay possible, so this milestone
proves the store rebuilds correctly from storage alone rather than from anything held in
memory.

Exercised through the coordinator and store from a CLI entry point against the live
harness, so that a created conversation's session id is a real one.

### Architecture

C8, C9, C11

Realised: C9 (Session Coordinator) gained the conversation-creation entry point that
provisions exactly one server session. C8 (Conversation Store) gained the versioned
persisted envelope, its unknown-version rejection, and `deleteConversation`. C11 (Storage
Port) is unchanged and needed no change. No deviation from the agreed architecture: session provisioning was
placed in C9 (which depends on C7 and C8) rather than C8, so C8 still depends on C11
alone and has no knowledge of the api client — verified by inspection, its only import is
`StoragePort`.

One deviation IS recorded, added in review cycle 1: C9's public surface gained
`createConversation`, which the written `C10 → C9` interface does not name. See the
`**M8 — ...**` entry under `## Deviations` in `.harness/architecture.md`. `Material: no`.

### Acceptance Criteria
- [x] (derived: FR3) Conversations can be created, listed newest first, opened and deleted,
      and a deleted conversation is gone after the store is rebuilt from storage.
- [x] (derived: FR3) Each conversation is backed by exactly one server session id, and
      creating a conversation creates exactly one session against the live harness.
- [x] (derived: FR3) The full transcript of each conversation is persisted locally and is
      recovered intact by a store constructed fresh from persisted storage alone.
- [x] (derived: FR3, Architecture C11) The persisted payload is written under a versioned
      key, and a payload written under an unknown version is rejected rather than
      misread.

`bun run src/host/m8-proof.ts` itself rather than crediting this record, and observed

### Follow-ups

- `test/web/session-coordinator.test.ts` declares `conversationIdFromError` in the
  correction test added by C2 and never reads it — dead code inside an otherwise
  load-bearing test. Raised as OPTIONAL by the cycle-2 reviewer, which confirmed it
  weakens nothing: every assertion in that block was proven load-bearing by mutation, and
  `tsc --noEmit` passes because `noUnusedLocals` is not enabled. Cosmetic; not worth a
  correction cycle of its own, so left for a future pass.
- Nothing at runtime catches `UnknownStorageVersionError`. The store now throws where it
  previously returned an empty list, so an app whose stored payload is unreadable will
  surface a raw exception rather than a handled state. Raised by T1 and deliberately left
  out of M8's scope — M9 owns the UI wiring and is the natural home for turning this into
  a user-facing state. Recorded so it is not lost.
- No migration path from the pre-envelope bare-array payload was written, by explicit
  instruction in T1's packet: no released data exists, so a migration would be untested
  surface. If any real device ever held the old format, its conversations will now be
  rejected rather than read. Revisit only if that becomes possible.
- `{"version": 1, "conversations": "not-an-array"}` is rejected through the same
  `UnknownStorageVersionError` path with `foundVersion: 1`, so the error message names a
  version that did in fact match. Consistent and safe, but the message is slightly
  misleading for that one shape. Cosmetic; no test exercises it.
- The untracked-source condition (see Baseline) keeps costing every verifier and reviewer
  a special-case warning. M6's Follow-ups already recommended committing the working tree
  so diffs are computable. It is still not done, and this milestone paid the tax again.
- `deleteConversation` THROWS `Conversation not found: <id>` for an unknown id. That is
  internally consistent with every other mutator, and was a deliberate, tested choice —
  but a UI delete button that fires twice, or races a rebuild, will surface a raw throw.
  M9 owns the UI wiring and should decide whether the UI guards it or the store softens
  it. Same class of issue as the unhandled `UnknownStorageVersionError` above.
- Deleting a conversation removes it locally but does NOT delete the server session it was
  backed by. Nothing in FR3 or M8's criteria asks for that, so it was correctly left out
  of scope, but it means sessions accumulate on the harness. Worth a decision later.
- `test/web/conversation-store.test.ts`'s newest-first rebuild test orders conversations
  using real 5ms sleeps to force distinct `updatedAt` values. It passes reliably and the
  ordering is the reverse of insertion order so it cannot pass vacuously, but time-based
  ordering tests are the kind that go flaky on a loaded machine. Cosmetic; noted only.
- Cycle 1's review explicitly re-raised, as an OPTIONAL finding, the two items above that
  M8 deferred to M9: nothing at runtime catches `UnknownStorageVersionError`, and
  `deleteConversation` throws on an unknown id. The reviewer's suggested correction was
  "None needed for M8 itself; confirm M9's task packets pick these up." No M8 correction was
  made for either. M9's packets must cover both, and this line is the record that a reviewer
  asked for it rather than it merely having been noticed once.
