read-only regions and `web/src/main.ts` discards the handle `mount()` returns, so the served

list and chat view, **and translate user actions into coordinator calls**"

**Every acceptance criterion here is derived.** All eleven of the requirements' own ACs are

**T3 — generation progress drives repaint (criterion 2).** Accepted at the **Mid** tier on
attempt 3, after both Cheap rungs failed. Worth reading before reviewing criterion 2, because
two of the three attempts produced green commands over tests that proved nothing.

*The real defect, which the packet itself had wrong.* The packet specified that `onComplete`
should call `controller.render()`. Reading `web/src/session-coordinator.ts` shows that is
impossible: `handlers?.onComplete?.(...)` fires at line 143 inside `consumeEventStream()`,
which returns at line 184, and only then does `send()` call
`conversationStore.appendTurn(...)` at lines 377-399. So a `render()` inside `onComplete` reads
a store that does not yet hold the assistant turn — and since `setStreamingText("")` has just
dropped the streamed projection, the transcript ends up **missing the assistant text
entirely**. Attempt 1 substituted its own ordering, which had the identical flaw.

*The fix.* `onComplete` and `onCancelled` now set only the generation state. The
`actions.send(...)` promise's `.then()` does `setStreamingText("")` then `controller.render()`
— by which point `appendTurn()` has run, so the store genuinely holds the turn. `onError` still
clears inside the handler, which is correct: nothing is persisted on the error path.
`HarnessStreamError`'s human-readable message is `guidance.detail` (`api-client.ts:256-267`).

*Why attempt 2 was rejected despite an all-green suite.* Its two load-bearing assertions could
not fail on what they claimed. The exactly-once check counted assistant turns in the **store**,
so it would have passed against a completely empty DOM transcript — the precise bug just fixed.
The incrementality check used `toContain` membership over values taken from the `view` object
handed to `paint`, not from the document. Both now read the rendered happy-dom DOM: the
transcript element's `textContent` is counted for exactly one occurrence of the final text, and
per-delta DOM snapshots are asserted as an exact ordered sequence
`["He", "Hello", "Hello world"]`.

*Bite-checked, not asserted.* The verifier reproduced both mutations in throwaway copies of the
tree. Reverting the render into `onComplete` makes the exactly-once assertion fail with
`Expected: 1, Received: 0`. Batching the deltas so `setStreamingText` is called only once makes
the sequence assertion fail with `[null, null, null]`. Each assertion therefore has real power
over its own defect. `dom-target.ts` was restored byte-for-byte after the worker's own
bite check (md5 `65c857a55b2707fc50a682fc068c89bf`, confirmed before and after).

*Honest limit.* The delta-sequence assertion does **not** fail under the `onComplete` revert,
and the Mid worker reported this itself rather than hiding it. That is structural: the delta
path paints entirely before `onComplete` runs, so a mutation to `onComplete` cannot disturb it.
The two assertions cover different regressions; neither subsumes the other.
