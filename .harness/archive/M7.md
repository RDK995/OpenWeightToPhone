**Design decisions taken by this phase, so a continuation does not re-litigate them.**

*How "a distinct typed error" is read.* FR9 and the criteria are satisfied by four
error classes grouped by category - `HarnessApiError` (HTTP), `HarnessStreamError`
(SSE), `HarnessOfflineError`, `EmptyPromptError` - each carrying a `code` and its own
`ErrorGuidance` drawn from an exhaustive per-code table. Sixteen subclasses were not
created. What makes each condition *distinct* is enforced mechanically: the guidance
tables are typed `Record<HttpErrorCode, ErrorGuidance>` and
`Record<StreamErrorCode, ErrorGuidance>`, so a missing code fails `tsc`, and a test
asserts the eighteen `title`s and eighteen `detail`s are pairwise distinct. An
undocumented code falls back to guidance that embeds the code verbatim, so two unknown
codes still differ from each other. This reading is stated here so the reviewer judges
against it rather than inferring one.

*Where the taxonomy lives.* In `web/src/api-client.ts` (C7), whose agreed
responsibility is already "map every documented failure to a typed error". No new
component or file was introduced, so `.harness/architecture.md` needs no deviation
entry.

*What "surfaced" can mean at M7.* There is no UI yet - C10 is M9's and pairing is
M11's. M7's obligation is therefore that every documented condition reaches the
caller of C9 as a typed error carrying its own user-facing guidance. The
`unauthorized` -> re-pair and `queue_full` -> retry-later *guidance* is proven here;
the act of *rendering* it is M9's. This is the same boundary M6 recorded as a
follow-up, now closed on the taxonomy side.

*How the draft prompt survives an offline failure.* `HarnessOfflineError` carries a
mutable `draftPrompt`, which `send()` populates on its way out. `ConversationStore`
gained no draft field, so C8 is untouched and out of M7's architecture list correctly.

*The critical constraint, checked by the orchestrator directly as well as by the verifier.*
`isAbortError(error, signal)` returns true when `signal?.aborted === true`, or when the
error's `name` is `AbortError` or `TimeoutError`; the catch then does a bare `throw error`,
so **object identity is preserved** rather than re-wrapped. Tests assert strict equality
(`error === abortError`) for all three cases, including a pre-aborted signal paired with a
`TypeError`. M4's cancel and M5's resume are therefore untouched, and the 47
session-coordinator tests confirm it. The `signal.aborted`-first ordering can in principle
misclassify a genuine network failure that coincides with an abort, but it fails in the
conservative direction — the raw error propagates instead of becoming `HarnessOfflineError`
— so it cannot break M4/M5.
