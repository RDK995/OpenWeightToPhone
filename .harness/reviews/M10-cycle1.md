**Severity:** IMPORTANT

**Problem:** A failed cache write discards a successful network response. In `handleShellRequest`, `deps.cachePut` is awaited *inside* the same `try` as the network fetch, so if the cache write rejects (e.g. `QuotaExceededError` under iOS storage pressure/eviction) the already-in-hand 200 response is thrown away: with an empty cache the handler rejects and the document fails to load, and with a warm cache it silently serves the stale build the strategy exists to avoid.

**Evidence:** `/Users/ryankenny/Projects/phoneToLocalModel/web/src/sw.ts:46-74`, specifically the `await deps.cachePut(...)` at line 52 sitting under the `catch (error)` at line 65 that ends in `throw error` at line 73. Reproduced directly:

```
A: THREW -> QuotaExceededError quota   (document load fails despite a 200 from the server)
B: returned OLD BUILD                   (network-first silently degrades to the stale build)
```

No test in `/Users/ryankenny/Projects/phoneToLocalModel/test/web/sw.test.ts` covers a rejecting `cachePut`; the three tests whose `cachePut` throws all assert it is never called, so the path is entirely unexercised.

**Why it matters:** This is the shell handler for `/app/`, so the blast radius is the whole app: a cache-write failure makes the home-screen icon open a network error even though the Mac is up and reachable — the exact opposite of this milestone's stated outcome ("the app is there whenever the phone is picked up"), and squarely FR2's "installable and loadable". Caching is an optimisation and must never be able to fail a request that already succeeded.

**Suggested correction:** Move the cache write out of the success path's failure surface — `void deps.cachePut(request, networkResponse.clone()).catch(() => {})` (or wrap it in its own `try`/`catch`) before `return networkResponse` at line 54, so a rejected write is swallowed and the fresh response is returned regardless. Add a test to `test/web/sw.test.ts` with a rejecting `cachePut` asserting the fresh body is still returned in both the empty-cache and warm-cache cases.

**Severity:** OPTIONAL

**Problem:** `https://<host>/app` without a trailing slash serves `index.html` at path `/app`, where the shell's relative `href`s resolve to the origin root and 404/401 instead of loading.

**Evidence:** Live: `GET /app` → `200 text/html` with no redirect; `GET /main.js` → 401; `GET /app.webmanifest` → 401 (the harness owns the root and rejects unauthenticated requests). The relative references are `/Users/ryankenny/Projects/phoneToLocalModel/web/public/index.html` lines 19 (`href="./app.webmanifest"`), 20 (`href="./icons/apple-touch-icon-180.png"`) and 30 (`src="./main.js"`). The `/app`→`index.html` mapping is `stripMountPrefix` at `/Users/ryankenny/Projects/phoneToLocalModel/src/host/pwa-server.ts:17-23`, which is pre-existing C4 code M10 did not touch — but M10 added two of the three broken references.

**Why it matters:** A human typing the URL without the trailing slash and choosing Add to Home Screen gets an icon that opens a blank page with no manifest — and, with no manifest, plausibly not standalone either. The sanctioned path is safe (`pairingUrl()` in `src/host/config.ts:80-85` emits the trailing slash, and the attested install worked), so this is a trap rather than a live defect, and the mapping predates M10.

**Suggested correction:** Either make `resolveAssetPath`/`handleRequest` 301-redirect a bare `/app` to `/app/`, or switch index.html's three `href`/`src` values to absolute `/app/...` paths, matching the convention the manifest already uses for its icons.

**Severity:** OPTIONAL

**Problem:** `test/icons.test.ts` calls `generateIcons()` with no `root`, which writes into the repository's own source tree, and it does so *before* asserting — so the test regenerates the committed icons and then validates its own fresh output. It cannot fail on icon drift, and running `bun test` mutates `web/public/icons/`.

**Evidence:** `/Users/ryankenny/Projects/phoneToLocalModel/test/icons.test.ts:41-42` and `:207-208` both call `generateIcons()` unrooted; `/Users/ryankenny/Projects/phoneToLocalModel/scripts/generate-icons.ts:218` defaults `root` to the repository. Observed: the three PNGs' mtimes advanced to my `bun test` run.

**Why it matters:** Low real risk — generation is deterministic and I confirmed the bytes are unchanged (9264 / 33143 / 7997, matching the recorded and live-served sizes) — and `test/web/manifest.test.ts` does read the on-disk files independently. But a test suite that writes into source is a hazard, and the "did the checked-in icons come from this generator?" property is not actually being tested.

**Suggested correction:** Point both calls at a temp root (the second test already creates one) and assert the checked-in `web/public/icons/*.png` bytes equal the freshly generated ones, rather than overwriting them first.
